# 2026-09-27 工作日志

## 1. 前端 worker+wasm 加解密工具（@encv/crypto）

- 需求：VuePress / Obsidian / 思源插件共用一套加解密，**严禁各写一套**。
- 方案：**不重写算法**，把 `internal/v2/crypto` 编译成 WASM（`GOOS=js GOARCH=wasm`），前端只做加载与调度 → 字节级对等是结构上必然，而非靠测试保证。
- 交付：`internal/v2/crypto/simple`（ENCVS1 信封）+ `cmd/encv-wasm` + `cmd/encv-crypto-vectors`（黄金向量）+ `app/packages/encv-crypto`（core/worker/client + 三宿主 adapter）+ `make wasm`。
- 坑与决策：
  - Go wasm 导出函数**必须返回结果对象**，不能抛异常——异常跨 `syscall/js` 边界会打死整个 wasm 实例（Worker 里后续调用全部失效）。Go 侧对入参做类型防御（坏参数只让本次调用失败），并有对应回归用例。
  - worker 源码**不 import 任何资源**（wasm/胶水由主线程经 init 消息送入），才能被 Vite/esbuild/rollup 任意打包器复用。
  - wasm 3.3MB（gzip ~950KB）：约 1MB 来自 `internal/v2/types` 间接引入的 zstd/cbor；要瘦身应抽 `crypto/primitive` 叶子包让 `crypto` 委托，**不要**在 TS 侧另写实现。
  - 契约锁：Go 测试与前端测试读同一个 `vectors.json`，任一侧改参数两边同时红。

## 2. 借鉴 Cordis 收敛插件系统（只借两条性质，不引入 DI 容器）

- 借的两条：**副作用可逆**（Disposable 可选接口）、**生命周期包含**（卸载逆序；失败隔离不拖垮其它插件）。
- 判断依据（请勿扩大化）：ENCV 插件是编译期装配 + 进程内长驻，完整 IoC/DI 容器收益远小于复杂度。
- 产物：`lifecycle.go`（6 态状态机）+ `capabilities.go`（3 个可选能力接口取代 `registry.go` 里对 `*video.VideoPlugin` 的 3 处特判，配源码扫描守卫测试）+ `video.Dispose()` + `Server.Stop()` 停机回收 + `/api/plugins` 下发 state/error/disposable。
- 决策：`Disposable` 做成**可选接口**而非加进 `Plugin` 胖接口，7 个插件可逐个改造不必一次到位。
- 核实结论：**只有 video 需要 Dispose**。其余插件只 `MkdirAll(outputDir)`（用户输出目录，绝不能删）；alist_encrypt 的 `*.alistenc.tmp` 在自身失败路径与 rename 失败时都已 `os.Remove`。**不要为了凑数加空 Dispose**。

## 3. 修掉 copy/move/rename 静默覆盖（回归，非特性）

- 根因：commit `16ca9e8` 把同步 handler 换成异步任务时，**把 `os.Stat(dest) → 409` 的冲突校验一并删了**，而新 `file_task_handler.go` 用 `os.Create`（截断）+ `os.Rename`（POSIX 静默替换）→ 静默覆盖。
- 判定为回归的三方证据：`.trae/specs/task-system-rollback-and-file-ops/spec.md:576` 明确写「move 到已存在目标 → 期望 failed」；前端 `useFileSystemTests.ts` 用例 5 同样期望；`CopyRollbackStrategy` 只 `os.Remove(target)`，覆盖后回滚会删掉用户原文件（比覆盖更糟）。
- 不能简单恢复 HTTP 409 的原因：前端现有契约是「202 + 任务 failed」（用例 5 依赖能拿到 taskId）；且 HTTP 层 stat 与任务执行间有 TOCTOU。→ 校验落在 `FileTaskHandler.prepareDestination()`（任务执行前，唯一可靠防线）。
- 覆盖语义（P1）：默认拒绝；`overwrite: true` 时**先把目标 MoveToTrash**（条目 task_id 指向本任务），回滚时按原任务 ID 还原并清理条目；无 TrashManager 或其 store 为空则拒绝覆盖（fail-safe）。
- `MobileTask.Overwrite` 不落库：重启丢失后按默认拒绝——丢失方向安全。

## 4. 顺带修掉的 3 个真实缺陷（都是测试先红才发现的）

1. **copy 到自身路径会截断成 0 字节**：`os.Create` 先把目标清空，src==dst 即自我销毁 → `prepareDestination` 对 copy 拒绝 src==dst（move/rename 仍视为 no-op）。
2. **`TrashManagerImpl.MoveToTrash` 在 `store == nil` 时 panic**：server 启动早期 `NewMobileService(..., nil)` 就是 nil store → 改为前置检查返回错误（不落库 = 不可还原 = 拒绝）。
3. **server 包测试被 SIGSEGV 打断**（`TestHandleFileCopyGin_Success`）：测试 setup 只填 `servingDir` 没注入 `mobileSvc`；且该文件的契约仍停留在「同步 200 + File copied」。补齐 `mobileSvc` + 改异步契约后，server 包从"跑不完"变成 113 PASS / 1 FAIL。

## 5. 方法论沉淀（本次反复验证有效）

- **不猜行为，先观测**：copy/move 的「目标已存在」到底是覆盖还是失败，用临时探针实跑拿到真实终态（202 + completed/failed），再据此写断言；用完删探针。
- **改契约前先找规格与前端契约**：三方（后端旧实现 / 规格 / 前端 E2E）一致才敢改；不一致时以「当前前端契约 + fail-safe 方向」为准。
- **生成产物别混进功能提交**：`i18n-tool gen-types` + `compile-android` 会把此前累积的过期内容一起带进来（本次 49 行无关 Android 字符串 + 3700 行类型重排）。本次改为复用已有 key、不新增 key，并 `git checkout` 还原生成产物；需要新增 key 时应单独跑生成器提交。
- **cmd_run 参数校验偶发失败**：含 `.trae` 路径或超长 `-m` 提交信息时，`cmd_run` 会返回 `arguments must be a valid JSON string`；此时可回退 `execute_command` 执行该条命令（属调用异常，非门禁拒绝）。另外 `grep X file` 偶发同样报错，换 `grep -E` 或加 `head` 可绕过。
