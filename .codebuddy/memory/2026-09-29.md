## 3. 实现（主线 writer 里做，wasm 侧只做薄封装）

- `internal/v2/writer/stream_v4.go`：`V4StreamWriter`（io.WriteCloser）+ `V4StreamSink`。
  - **为什么放在 writer 而不是 wasm cmd**：cmd 是 `Go build js/wasm` 专用，
    Go 单测覆盖不到；放主线才能有回归锁（本仓既定原则：wasm 侧不写密码学/容器逻辑）。
  - **为什么 Sink 不是 io.Writer**：容器头必须先于数据出现，但头里的
    ManifestOffset/GlobalCRC32 只有写完全部数据才知道 → 约定「数据段 Append 出去，
    最后 Finish(head, tail)」，调用方按 `head ‖ 碎块 ‖ tail` 组装。
  - 段布局**复用整块路径的 `writeOneSegment`**（只投影它真正读的两个字段），
    漂移不可能发生； CRC32/HMAC/md5 全部增量计算。
  - **AES-CTR 是流密码**，同一个 `cipher.Stream` 连续 `XORKeyStream` 会推进 keystream，
    所以明文可以一片一片喂 —— 这是「不必攒整段」的技术前提。
  - 每段**必换 nonce**（CTR 复用 nonce = 二时间垫），测试里锁了唯一性。
  - 空输入也产出一个空段（reader 按 playlist 取段序列）。
- `cmd/encv-wasm-container`：新增 `encryptBegin/encryptWrite/encryptEnd/encryptAbort`，
  全部返回 `{ok,...}`。`encryptWrite` 把本次调用攒出的密文段吐给 JS；
  `encryptEnd` 交回 `head/data/tail`。
  - 嵌套返回 Uint8Array 是可以的：`Value.Set` 对每个值走 `ValueOf`，`ValueOf` 遇到
    js.Value 原样透传（此前文件里的注释说「嵌套结构传不到」并不适用于这种情况）。
- 顺手修掉一个潜伏 bug：整块 `encryptBytes` 的 manifest **没写 mac_salt**，
  writer 会自己再生成一个 → 加密用一个 mac_key、reader 派生的是另一个，
  一旦打开 EnableHMAC 就是「MAC 永远验不过」。现已显式写入 `MACSaltBase64`。

## 5. 顺带发现并修掉一个**静默损坏**（做浏览器外验证时撞上的）

现象：wasm / 流式 writer 产出的容器，用 `encv decrypt-v2` 解 →
**文件大小完全正确、内容全是乱码、全程不报错**（错口令倒是被正确拒绝了，所以更迷惑）。

根因（判别实验坐实）：
- 同一个容器用 Node 加载同一份 `encv-container.wasm` 打开 → 逐字节一致 ⇒ **容器本身没问题**。
- 两套内容组织层的 keystream 模型不同：
  - v4 **segment 栈**（wasm/流式 writer 产出）：每段一个随机 nonce，keystream 每段重置；
  - **fragment 栈**（CLI 插件路径 / `DecryptReaderFactory`）：整条逻辑流只用 KVI 里那一个 iv，
    `buildCTRStreamAtOffset(key, iv, absoluteOffset)`。
  密钥对、偏移对，只有 keystream 不对；CTR 没有认证标签 ⇒ 静默错误。

修复：`decryptReaderFactory.ensureSingleKeystream()`
（`internal/v2/reader/factory.go`）在建立工厂时校验：
- 所有 segment 的 nonce 为空（插件/CLI 自己的写入路径就是这样）→ 放行；
- 或恰好一个 segment 且 nonce == KVI iv → 放行；
- 否则显式报错并指明要走 `reader.OpenV4Container + NewSegmentSeekableReader`。
回归锁：`internal/v2/reader/factory_nonce_stack_test.go`（先红后绿：改之前工厂是"笑着接受"）。
验证：CLI 自身 encrypt-v2 → decrypt-v2 往返仍然 OK；wasm 产物现在报明确错误且**不再产出文件**。

## 6. 接着把根**修掉**（不只是拦住）

守卫只是"拒绝"，用户还是解不开自己的容器。真正的修法是让 fragment 栈支持 per-fragment nonce：

- `types.Fragment` 新增 `Nonce string`（base64，16B；为空 = 旧行为：KVI 的 iv + 全局偏移）。
- `container/handle.AdaptV4ToV2` 把每段 nonce 复制进对应 fragment。
- 读取端四条路径全部按分片重置 keystream：
  `SequentialSeekableDecryptReader.setupFragmentAt`（偏移取**段内** localOffset）、
  `VirtualSeekableDecryptReader.setupCurrentFragmentReader`、`BulkDecryptor.DecryptToFile`、
  `SequentialDecryptReader.setupNextFragmentDecryptor`。
  ⚠️ 细节：无法 seek、靠 discard 推进时，段内 keystream 偏移必须是 **0**（自己会走掉 localOffset）。
- 守卫相应**降级**为适配层自校验 `ensureNonceIsCarried()`（nonce 没跟过来才报错），
  早先"多段即拒绝"的版本已被此方案**取代**（不再需要拒绝多段容器）。
- 验证（真实 CLI，不是单测臆想）：`encv decrypt-v2` 解 wasm 流式产物
  **16MB / 512MB 逐字节一致**（`MATCH 536870912`）；CLI 自身 encrypt→decrypt 往返照旧 OK；
  reader / writer / container/handle / types 四包全绿。
- 于是最初的目标也顺带达成：**1GB 级产物的内容正确性可以在浏览器外用 CLI 验**
  （不受 wasm 线性内存上限限制，之前 Node 内核验到 1GB 就死）。

## 7. 打通读取侧的增量供给（openStream）—— 大容器不再整体进内存

协议：**同步**的「内核声明缺口 → JS 喂字节 → 重试」，不是回调（理由见下）。

实测同一个 1GB 容器：
```
流式 openStream   : ok, 明文 1073741824 字节, JS 堆增量    4 MB
整块 open(bytes)  : ok, 明文 1073741824 字节, JS 堆增量 1012 MB
```

踩坑清单（每条都是真实失败换来的）：
1. **Go/wasm 不能在导出给 JS 的同步函数里挂起等 Promise**。
   第一版让内核调 `read(offset,length)` 拿 Promise 再阻塞等结果 → Go 程序直接退出，
   之后每次调用都是 `Go program has already exited`。必须反过来：内核只声明 need。
2. **`syscall/js.ValueOf` 不认识自定义结构体**：直接把 `[]ByteRange` 塞进
   `map[string]interface{}` 会在 `Value.Set` 里 panic，同样打死内核。要转成
   `[]map[string]interface{}` / `[]interface{}`。
3. **明文长度不能再"解密后累加"**：段栈的 `plainLength` 原本要读完整容器，
   1GB 容器会把 64MB 字节缓存挤爆、反复索要同一段（活锁）。改为按段头算术求长
   （`opened.segmentPlainLength`，有 zstd 段才退回完整读）。
4. **喂字节的缓存要按字节预算淘汰，不能按块数**：`info()` 逐段读段头，
   1024 段的容器按块数淘汰会把前面的段头挤掉 → 永远喂不完。
5. **"活锁"判定不能只看补字节次数**：1024 段补一千次是正常的，
   判据应是"同一缺口被反复索要"。
6. **忘 await 传 Promise 给 `streamFeed` 会 panic**（`Value.Int()` on undefined）。
   已加参数类型校验；同类教训：wasm 内核的每个入参都要先确类型，一次 panic = 内核全废。
7. 诊断用的 `println` 千万别打在高路径上：百万级 console 输出能把用例拖成"假死"。

## 8. 最后一公里：字节供给接到 HTTP Range

`read` 换成 `fetch(url, {headers:{Range}})` 即可，内核完全不知道字节从哪来。
1GB 容器实测：**只下载 3.2MB（1031 个 Range 请求，19s）就打开并读到了头/中/尾三个窗口**，
网络流量只有文件的 0.3%。

- `app/enc-preview/serve.py` 加了 Range（206 + Content-Range）—— 静态服务不支持 Range 的话
  `fetch(Range)` 会拿到整个文件，"不整体下载"这条就在网络这一环上漏掉了。
- 第一版代价：1024 段各读一次段头 ≈ 1000 个 Round Trip（19s）。已优化（见下）。
- **内核求"明文总长"不再读遍段头**：改抽样首段+末段（开销一致就统一推算），
  打开+info 的请求数 1028 → 6，耗时 18.8s → 0.15s。
  ⚠️ 真正的坑在 `plainLength()`：它把 `segmentPlainLength` 的失败**吞掉**并退回
  `plainAll()`（读全文兜底），于是抽样省下来的请求又被兜底悄悄花掉 ——
  **"还缺字节"(errNeedBytes) 必须原样上抛，不能走兜底**。
- 主线 `SegmentSeekableReader` 构造时逐段读段头 → 加 `samplePlainSizes`（抽样首/中/末）。
- ⚠️ **同一类坑第二次出现**：抽样时"字节还没供给"被当成"抽样不适用"退回逐段读 →
  每次重试只多命中一个段头 → O(n²)，实测 1GB 容器 **13 万次** readSegmentHeader。
  修法：主线新增 `reader.NeedBytesError` 约定（内核 `errNeedBytes` 实现 `IsNeedBytes`），
  缺字节一律**上抛**。
- 最终实测（1GB 容器，HTTP Range）：请求数 **1031 → 10**，耗时 18.8s → 0.14s，下载 3.1MB。
- 页面新增「容器 URL + Range 流式打开」入口与一条自检（有样例才跑，没有就跳过）。

踩坑：harness 里把口令写死在 spawn 参数里（"stream-probe"），改默认口令后忘记同步 →
外部校验一直报 wrong password；另外同名文件下载是边下边写的，旧内容会被抢先读到，
落盘要用唯一文件名。**口令/路径这类常量只应有一处定义。**

## 下午：反哺主应用（CLI + Capacitor）—— 三条被实测推翻的预期

### 主应用的真实形态（别再只想到 CLI）
- **CLI**：`cmd/encv` → `pkg/encv`
- **Capacitor 移动应用**：前端 `app/encv-mobile`（`src/api` + `GoProcess` 插件）启动
  **内嵌 Go 后端** `cmd/encv-mobile` → `encv.NewServer` = `internal/server`。
  所以"主应用"有两个落点，后端那条才是移动端真正在走的。

### 预期 1：「主应用加密是整块的，需要反哺流式」→ 错
- 插件 `TextPlugin.Encrypt` 只是准备上下文，真正的写在 `postEncryptDirect`：
  `for { src.Read(buf) → XOR → tempWriter.WriteFragmentData }`，**定长缓冲直落临时文件**。
- 解密侧 `io.Copy(outputFile, decryptedReader)`，同样流式。
- **结论：主应用本来就流式，不要重复造。**反哺点应是"统一编排 + 双向互认"。

### 预期 2：「流式一定更省内存」→ 错（实测）
40MB / 400MB 文本，采样进程峰值 RSS：
  - 插件路径：3.2MB → 27MB（**随文件大小增长**）
  - 流式路径（4MB 段）：44MB → 47MB（恒定，但基线高）
  - 流式路径（1MB 段）：31MB → 33MB（已采用）
交叉点在 **500MB~1GB**：小文件插件路径更省，只有 GB 级流式才有明确优势。
（流式基线高是段缓冲 + Go GC；段大小从 4MB 调到 1MB 能省约 13MB。）

### 预期 3：「移动端播加密视频要先解密落盘」→ 后端能力早就有，是**前端没接**
- 后端 `/stream`、`/decrypt` → `ContentHandler.ServeFile` 支持 **HTTP Range**
  （parseRangeHeader + seek + 206）。
- 但 `FilePreview.vue` 里：图片走 `getFileStreamUrl`（后端流），
  **视频/音频原生分支却把容器路径直接给 mpv** → mpv 不认 `.sccgv`，根本播不了。
- 修复：交给 `getAbsoluteStreamUrl(path)`（**必须绝对 URL**：DEV 下
  `getFileStreamUrl` 返回相对路径，mpv 在独立原生进程里解析不了）。
- 实测（起 `encv start -c cfg`，40MB 容器）：`Range: bytes=1000000-1000999` → 206，
  `Content-Range .../40000000`（总长是**明文**长度），与明文同偏移逐字节一致；
  跨 1MB 段边界同样一致；不带 Range → 200 + 40000000 字节。

### 环境 / 工程事实（下次直接复用）
- **vitest 用显式 include 列表**：新测试文件必须登记进 `FAST_INCLUDE`
  （`vitest.config.ts`，以 `themeCustomization.test.ts` 结尾那个数组），否则
  "No test files found"。环境是 happy-dom（有 localStorage/window）。
- **Go 测试必须走 `bash scripts/test-go.sh`**：裸 `go test` 会被守卫拦截。
- 测插件（`plugins.DecryptContainerWithPlugin`）时：
  ① 必须先 `p.Initialize(ctx)`（否则 `p.cfg` 为 nil → 取口令**空指针 panic**）；
  ② ctx 的 Config 要带 `PluginSettings`（如 `{"text": json.RawMessage(...)}`），
     否则 Initialize 报 "no settings found"；③ 输出目录要自己 `MkdirAll`。
- `plugins.PredictEncryptOutputName(inputPath, cfg)` 在 `internal/v2/plugins/registry.go`
  （不是 config 包）。未知扩展名（如 `.bin`）没有插件 → 流式通道走不了。
