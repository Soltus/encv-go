- **根因（不是猜的，被先红后绿的复现锁死）**：

  ⇒ 表现为"构建卡死"。
- **反面教材（我的第一版 init script）**：去改 `dependencyResolutionManagement`
  ⇒ 把 JitPack 独占解析弄丢 ⇒ `com.github.getActivity:EasyWindow` 解析失败。
  **不要动工程那套已经正确的配置。**
- **可用修法**：`scripts/gradle-buildscript-mirrors.gradle`（`-I` 传入，
  `./gradlew -I /workspace/scripts/gradle-buildscript-mirrors.gradle assembleDebug`）——
  只处理"**已自带 repositories 的模块**"的 buildscript/项目级仓库，**不碰 settings 与 app**
  （否则会凭空造出项目级仓库，反而盖掉 settings 里正确的配置）。
  效果可证：依赖缓存从 3.6M → 416M。
- **诊断手法（好用）**：`jstack <daemon-pid>` 看 `Daemon worker` 停在
  `ErrorHandlingModuleComponentRepository.tryResolveAndMaybeDisable` ⇒ 就是仓库解析在退避重试，
  不是"编译慢"。

## 3. P2c R11：单 peer 并发上限（含一个并发写 websocket 的真 bug）

- **做了什么**：`Caller` 加在途槽位（`MaxConcurrentCallsPerPeer=4` + `ErrPeerBusy`），
  search / file / agent-invoke 三处超限 → **429 `peer_busy`**；`SetExclusive`（一个 peer 只留一条活跃会话）
  + `DeleteConn`（按**连接身份**删除）。
- **⚠️ 背压不是故障**：`peerBusyIfErr` 必须**先于** `peerCircuitRecord` 判定且**不计入**熔断失败累计
  —— 否则一次限流就把健康对端熔断掉（限流自己打自己）。
- **⚠️ 竞态点**：`SetExclusive` 顶掉旧连接后，旧连接的 `defer` 若按 peerID 直接 `Delete`，
  会把**顶替它的新连接**一起删掉 ⇒ 必须按连接身份删（`DeleteConn`）。
- **真 bug（并发测试现形）**：`panic: concurrent write to websocket connection` ——
  Edge `handleRequest` 每个请求各起 goroutine 直接 `conn.WriteJSON`；此前单调用串行从未暴露，
  R11 允许 4 路并发后必崩。修：Edge 增 `writeMu` 串行化**所有**写帧（res / 心跳 ping / SendJSON）；
  Hub 侧 `handlePeerlinkWS` 的 hello_ok/pong/error 也改走 `peerConns.WriteJSON`（复用连接表写锁）。
  ⇒ **教训：连接表里已有的写锁，handler 里手写 `conn.WriteJSON` 会绕过它**，写帧必须统一入口。
- **验证**：`TestPeerlinkSearch_PerPeerConcurrencyCapped_429` + `TestPeerlinkWS_SingleSessionPerPeer`
  （先红：8 路并发 0 个 429 → 后绿）；`./internal/server` 整包 OK、`./internal/peerlink` OK、`go build ./...` OK。

  T9 重启后信任失效 + 老票据不可复用 + 自动重连 / T10 401 + 审计脱敏）⇒ 并发上限与写帧串行化改动无回归。
