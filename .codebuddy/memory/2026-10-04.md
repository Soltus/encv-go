## 1. `.codebuddy/skill-registry.json` 的 updatedAt 噪音 —— **源头修好**（不是靠 git hook）

- **现象**：IDE/MCP 每次扫描技能目录就把全部条目的 `updatedAt` 刷成同一时刻，
  而内容指纹 `hash`（= SKILL.md 全文 sha256）一个都没变 ⇒ `git status` 常年挂红。
- **⚠️ 我第一版做错了（用户当场指出）**：写了 `scripts/normalize-skill-registry.py` +
  `.git/hooks/pre-commit` 去"事后归一化"。用户一句"git hooks 不算真正解决方案，源头 MCP 代码
  就在当前项目" ⇒ 正确做法是**改写文件的那行代码**。
  （教训：先问"谁在写"，再谈"怎么消音"；能用源头修的，绝不上 hook / 事后补偿。
   我当初 grep 就走了弯路：codemogger 对这个 .mjs 返回空集，我没换关键字就误判"写方不在仓库内"。）
- **真源头**：`scripts/skill-manager.mjs`（app-dev MCP 用它管理技能），两处硬伤：
  ① `scanAndSync()` 里 `updatedAt: new Date().toISOString()` —— **无条件刷新**，不管 hash 有没有变；
  ② `saveRegistry()` 无条件 `writeFile` —— 内容一字不差也重写一遍，mtime 变了 git 就显示 modified。
- **修复（已落地）**：
  ① `updatedAt`：内容未变（`hash` + `path` + `displayName` + `description` 全同）⇒ **沿用 prev.updatedAt**，
     只有真变了才写当前时间；
  ② `saveRegistry()` 改为**幂等写**：序列化结果与磁盘内容相同就**不落盘**（返回 false），连 mtime 都不动。
- **验证（真实跑 MCP 代码，不是推断）**：`node` 载入 `skill-manager.mjs` 调 `loadRegistry()` + `scanAndSync()`
  ⇒ 扫到 40 个技能，registry 的 **md5 与 mtime 完全不变**（根本没写盘）。
  反向实验：临时改一个 SKILL.md（hash 变）⇒ registry md5 变 + updatedAt 刷新 ✔（真变更没被吞）；
  改回原文后再扫 ⇒ 再刷新一次（合理：内容确实又变了一次）。
- **清理**：`.git/hooks/pre-commit` 已删除（源头修好后它就是多余的"绕"）。
  `scripts/normalize-skill-registry.py` **保留**，但定位降级为：历史遗留一次性清理 + `--check` CI 校验，
  不再是解决方案本身。

## 7. 真机回归（装 APK 后）：两个我自己引入的 bug + 一条验证方法论

  **教训**：Capacitor 权限回调与插件方法是两套注解，混用会让权限申请这一步就抛错。

## 9. 远程调试压测：11 个缺陷 + 已修 3 个 P0（2026-10-04）

- **方法**：对配对的安卓真机（2025 后端）打 A–W 共 ~30 个用例（只读工具、边界、鉴权、并发、重放、联邦搜索、远端读）。先挖缺陷、再逐条修。
- **❗踩到的两个认知坑（修BUG 前必读）**：
  ① **扫了一半的成果被丢弃**：`scanDirForIndex` 被 ctx 打断时是 `return entries, ctx.Err()`
     （**条目已经返回了**），但调用方 `if err != nil { log; return }` 整批丢掉
     （真机日志 `FTS5 background scan failed err=context deadline exceeded scanned=9597`）。
     ⇒ **这类 scan/collect 函数返回 (部分结果, err) 时，务必先看 len(result) 再决定要不要丢**。
  ② **已超时的 ctx 不能拿去做下一步 IO**：同一个 ctx 在插入阶段 `BeginTx` 会立刻
     `context deadline exceeded` ⇒ 修了错误处理也会在插入再失败一次。**换用新 ctx**。
- **已修并提交（`8ed5f09b`）**：
  1. **索引构建**（`mobile_search_fulltext.go` + `fts/fileindex.go`）：保住部分成果入库；
     新增 `MarkPartial()`（**刻意不更新 IndexedAt**）；启动判据 `TotalFiles>0` →
     `TotalFiles>0 && IndexedAt!=""`，这样 part 之后会继续补齐而不是被 skip 掉
     （旧逻辑会造成"永远建不完"的死循环）。BulkInsert 是 INSERT OR REPLACE ⇒ 续扫幂等安全。
  2. **远端读静默截断**（真机实测 587822 字节被截成 262144 且 HTTP **200** 无任何标记）：
     根因不是 RPC bug —— `DefaultReadChunk=256KB` 是刻意的**分片**设计（E4/R13），
     **错的是 HTTP 适配层没表达分片语义**。修：`ReadResult` 加 `Total`；非最后一片返回
     **206 + Content-Range**；对端取不到总长时按 RFC 7233 给 `bytes s-e/*` 的 206（绝不谎称完整）。
     `OnRead` 签名改为 `(data []byte, total int64, err error)`（牵连 3 个 call site + 测试）。
  3. **联邦搜索暴露索引状态**：新增 `indexState`(building/empty/partial/ready) + `indexedFiles`；
     Hub 侧**向后兼容**旧 APK 的纯数组返回体（宽容解析）。
- **测试**：`scripts/test-go.sh ./internal/server/`（整包 OK 86s）、`./internal/fts/`、`./internal/peerlink/`。
  `peerlink_file_test.go` 里"分片读期望 200"的**旧契约是错的**，已改为期望 206+Content-Range，
  并补 `LastChunk_200` / `UnknownTotal_206` 两个反向锁。
- **⚠️ 环境事实**：`scripts/test-go.sh` 的 pre-flight **会杀掉占用 2025 的后端进程**
  （这次就把正在联调的后端杀了）⇒ 跑 Go 测试前先停联调，测完要手动重启。
  且 **peerlink 的 peer/token/psk 全在进程内存** ⇒ 后端一重启，**已配对设备必须重新扫码**，
  这是重启的真实成本，别当成"又出 bug 了"。
- **❗又一个一维错误观（第三次踩同一类）**：`go test` **必须带 `-short`**，否则 server 包会
  `panic: test timed out after 300s`（它单包完整跑 376s+）。官方脚本 `scripts/test-go.sh`
  默认就加了 `-short` —— 用 `ENCV_TEST_BYPASS_GUARD=1 go test` 绕守卫时**必须手动补 `-short`**，
  否则会误判成"我的改动把测试跑挂了"。带 -short 后：server 103s ok / peerlink 2s ok / fts 60s ok。
- **bypass 守卫的好处**：pre-flight 会 kill 占用 2025 的后端（这次正规脚本就把联调中的后端杀了），
  单测时用 `ENCV_TEST_BYPASS_GUARD=1` 可以**保住后端不断连**（代价：自己补 `-short` 等 flag）。

## 9b. 熔断连坐已修（续 §9，`ffc82455`）

- **缺陷**：连续 2 次路径非法就把 peer 熔断开路 ⇒ 之后**合法**请求全 503，整条远端读链路瘫到冷却结束。
- **通用教训（值得迁移到别处）**：跨进程调用时，**错误不能只靠字符串过 wire** ——
  sentinel 会在传输中丢失，上层只能一律按"故障"处理，于是"你请求写错了"被当成"对方挂了"。
  ⇒ 需要在协议里留一个**错误类别**字段；本项目就是给 res 帧加 `errKind`。
- **修复三件套**：① wire 加 `errKind`（旧对端不带 ⇒ 空串 ⇒ 沿用旧语义，**向后兼容**）；
  ② `peerlink.ErrPeerRejected` sentinel，RPC 层据 errKind 用 `%w` 重建以便 `errors.Is`；
  ③ Hub 侧 `peerRejectedIfErr` → **400**（不是 502/503）+ `peerCircuitRecordSuccess`
  （对端健康地回话 = 链路可用证据，应**复位**失败计数，而不只是"不计入"）。
- **熔断语义原则**：只对**网络/可用性故障**（离线、超时、连接断）生效；
  入参非法、权限不足、文件不存在这类"对端明确拒绝"**一律不得计入**。
- **回归锁**：`TestPeerlinkFile_RejectedNotCircuitBreaker`（6 次非法路径后合法请求仍须成功）。
  **已做先红验证**：stub 改回 `errors.New("bad_path")`（不带 sentinel）时第 1 次就 `got 502` FAIL
  ⇒ 证明这条锁真的抓得住 bug，不是摆设。

**压测清单里仍未修（留给后续决策）**：
- 限流 agent invoke **10 次/分钟**过低，交互式远程调试极易撞到（冷却 ~60s）
- **`callId` 不幂等**：同一 callId 重复提交 ⇒ 工具被执行两次（只读无害，写类工具是真事故）
- **发起端无审计**：`/agent/audit` 只读本进程 approver，跨端调用发生在执行端 ⇒ 桌面永远查不到自己发起过什么
- **HTTP 契约不一致**：业务失败有时 `ok:true + result.error`，有时 `ok:false + error`（UI 极易漏判）
- **内部细节泄漏**：Go struct 定义 / 手机绝对路径 `/storage/emulated/0/...` / SQL 文本（fts5 语法错）直接回给调用方
- **参数命名不一致**：工具用 `rel_path`，`/peerlink/file` 用 `path`
- **联邦搜索的 fts5 查询未转义**：`q` 含特殊字符时仍是 502 + SQL 语法错（需与 rejected 语义统一成 400）
  （`/agent/audit` 只读本进程 approver，跨端调用发生在执行端）；HTTP 契约 ok:true/false 不一致；
  内部错误信息透出（Go struct 定义、手机绝对路径、SQL 文本）。
