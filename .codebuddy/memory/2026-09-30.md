## 移动端大附件：上传链路实测定界（先测再改）

结论先行：**移动端上传/加密本身是流式的，真正的天花板是 500MB 硬上限，且判定得太晚。**

### 链路形态（读码 + 实测）
- 前端：`uploadFile`（`app/packages/shared-components/src/api/encv_files.ts`）用 `FormData + File`
  交给原生 `fetch`，**不经过 ApiProxy**（ApiProxy 只服务 chat/SSE，它的 body 只能是 string）。
  实测 JS 堆增量 **0MB** —— WebView 侧没有把文件读进内存。
- 后端：`/api/files/upload` → `mobileSvc.UploadFile` → `io.Copy(outFile, content)` 流式落盘；
  采样进程 RSS 在 400MB 上传前后没有明显增长（峰值与基线一致）。

### 天花板（红证据）
`internal/service/mobile_service.go` 的 `defaultMaxUploadSize = 500MB`，而且是
**先 io.Copy 写完整文件、写完才判超限再 `os.Remove`**。chromium 走 FormData 实测：

```
600MB → 400 {"error":"file size (629145600 bytes) exceeds maximum allowed (524288000 bytes)"}
400MB → 200 成功
```

即：GB 级文件不是 OOM，是**根本传不进去**，并且 600MB 会白传白写一遍才报错。

### 改法（两道校验都在）
- `DefaultMaxUploadSize` 导出 + 新增 `CheckUploadSize(contentLength)`；
- `handleUploadFileGin` 在 `FormFile` **之前**用 Content-Length 早拒；
- `UploadFile` 里的后置校验保留（chunked 传输可能没有 Content-Length）。
- 回归锁 `TestCheckUploadSize`（`internal/service/mobile_service_errors_test.go`）：
  已验证**先红后绿**（把阈值改成 `*2` → FAIL，改回 → PASS）。
- 集成复验：早拒生效后报错字节数变成 **629145798**（含 multipart 封装的 198 字节）
  而不再是 629145600 —— 两种数字能直接区分走了哪条判定路径。

## wasm 体积：实测归因（别再凭直觉动刀）

单位 MiB。**基线（理论下限）**：Go wasm 空程序 1.58 / gzip 0.47 —— 低于这个数不可能，
除非换 runtime（TinyGo 之类），别把"降到 1MB 级"当目标。

| 产物 | raw | gzip -9 | brotli -11 |
|---|---|---|---|
| 空程序（基线） | 1.58 | 0.47 | — |
| 只含 pbkdf2/aes/hmac/sha256 的探针 | 2.23 | 0.64 | — |
| `encv.wasm`（crypto 内核） | 3.25 | 0.91 | 0.69 |
| `encv-container.wasm`（容器内核） | 8.15 | 2.18 | 1.59 |

手段与收效（都是实测，不是估计）：
- 抽 `crypto/primitive`：理论下限 = 探针的 **2.23** —— 印证了文档 §6 的"约 2.3MB"，
  但**只对 crypto 内核有效**（省约 1MB）。
- **真正的大头是容器内核 8.15MB**，primitive 抽取对它毫无帮助。
  它的构成：Code section 5.11 + Data 2.87（4605 个函数）。
- 去掉 5 个插件 import = 0.62MB。
- 给 `reader` 的远程 `net/http` 读取器加 `//go:build !js` = **0 字节**：
  依赖树里明明有 `net/http`/`x/net/dns`/`x/text`，但 Go 链接器的 DCE 早把它们裁了。
  （我加了 tag 又回滚：没有收益，只会引入 js/非 js 行为差异。）
- `-ldflags="-s -w"` = 0.06MB；`wasm-strip`（去 name section）= 0.17MB。基本无用。
- ✅ 最划算的是**传输层**：`app/encv-preview/serve.ts` 加 gzip 支持（8.15 → 2.18），
  brotli 可到 1.59（标准库没有 brotli，所以脚本用 gzip）。

⚠️ **Range 与压缩互斥**：Range 的 start/end 是压缩前的字节偏移，
206 响应一旦套上 gzip，客户端取到的是压缩流的区间，解出来的字节全错。
所以只压 200，206 原样发（已写进 serve.ts 的 docstring 与 README 已知边界）。

工具链：wabt（`wasm-objdump -h` 看 section、`wasm-strip`）与 brotli 已 apt 装好。
`go tool nm` 对 wasm 不可用（`unrecognized object file`）—— 别浪费时间。

### 3. 顺带修掉 wasm 在 Node 下的死锁（真实故障）
`node app/encv-preview/verify-container.mjs <容器> <口令>` 一打开容器就
`fatal error: all goroutines are asleep - deadlock!`，栈是
`logger.textHandler.Handle → os.File.Write → syscall.fsCall`。

根因：js/wasm 下写 `os.Stderr` 走 `syscall/fs_js` 的 `fsCall`，**需要主 goroutine 响应**，
而 wasm 内核的主 goroutine 永久阻塞在 `<-make(chan struct{})`（导出函数就是这么挂给 JS 的）。
浏览器里同样是 js/wasm，只是调用时机没走到这条写路径，所以一直没暴露。

修：`internal/logger` 拆出 `stderrWriter()` ——
- `writer_default.go`（`!js`）：`os.Stderr`（与原行为完全一致）；
- `writer_js.go`（`js`）：内建 `println` 的 `jsConsoleWriter`（runtime 输出**不经过 fsCall**）。
⚠️ 改完必须 `make wasm`，且 build-wasm.sh 的路径要同步（见上）。

验证：16MB 容器 `--pattern` 逐字节比对通过；浏览器自检 18/18；门禁 10/0。

## 流式 zstd：取舍选了「显式契约」（不是真做 seekable 流式压缩）

先复核事实，再定方案 —— 结论和文档里那句旧话不一样：

- compose（`internal/v2/container/compose`）**两条路都写死** `CompressionModeNone`，
  既没有入口能请求压缩，也没有任何报错。文档 §6 原写「需要压缩时只能走整块路径
  （CompressionMode 由调用方在整块路径侧决定）」—— **这句是错的**：compose 的整块同样不支持，
  真正能产出压缩容器的是**插件加密路径**（CLI encrypt-v2 / EncryptToTempFile_v2）。已改文档。

改法（选项 2：把隐含契约显式化，不做 seekable 流式压缩）：
- `Options.Compression` 字段 + `ErrCompressionUnsupported`：传非 none 一律报错，
  **被拒时不产出任何字节**（静默忽略的后果：调用方以为拿到压缩容器，实际没有 ——
  不失败、不告警，只有体积不对）。
- wasm 侧 `startEncrypt` 把 `opts.compression` 透传给 compose（此前这个字段根本没读）。
- 回归锁（先红后绿已验证：把校验短路成 `false` → FAIL 报「实际 <nil>」，还原 → PASS）：
  ①流式/整块请求 zstd 必须返回 ErrCompressionUnsupported；
  ②零值与显式 none 不得误伤；
  ③**zstd 通道本身必须能往返**（seekable zstd 段 + seek table，且密文确实更小），
    把「compose 不支持压缩」与「zstd 坏了」区分开 —— 后者会让存量压缩容器全部打不开。
- 浏览器自检同步加一条（19/19）：请求 `compression:"zstd"` 必须被明确拒绝。

⚠️ 压缩模式的常量是**字符串**（`crypto.CompressionModeNone = "none"`、`CompressionModeZstd = "zstd"`），
不是数值枚举（数值那边是 `types.ModeFlagCompressionZstd`，别混用）。

- 现象：真机上 `POST /api/preview-assets/import` 报
  `找不到该文件：stat /storage/emulated/0/data/user/0/com.encvgo.app/cache/preview_assets/xxx.zip`。
  注意这个路径是 **servingDir + app 私有绝对路径** 拼出来的，一眼就能看出是解析错了。
- 根因：原生把用户选中的 Uri 物化成文件后返回的是**应用私有目录的绝对路径**
  （`/data/user/0/<pkg>/cache/...`），它**不在任何挂载点内**；而 `resolveUserPath`
  遇到不在挂载内的路径会按**相对路径**处理，拼到 `servingDir`（`/storage/emulated/0`）上。
- 修：新增 `resolveImportPath` —— 先试挂载目录内，再试"后端可写目录"白名单
  （`filepath.Dir(previewAssetsDir())`、`config.AppDataDir("tmp")`、
  以及由 `ENCV_APP_FILES_DIR` 推出的 files 与它旁边的 cache）。越界绝对路径仍拒绝，
  且报错要列出"允许哪些目录"，否则下次换个目录还是只能猜。
- 原生侧同步改：物化目标 `cacheDir` → **`filesDir`**（cache 会被系统清空；
  且 filesDir 与后端 AppDataDir 同根，天然被允许）。
- ⚠️ 写测试时必须复现真机的**目录关系**（servingDir 与 private 互不相干）。
  第一版把 private 目录放在 servingDir 之下，`resolveUserPath` "碰巧"认下它，
  用例在坏代码上也是绿的 —— 差点留下一个测不出问题的回归锁。

### ④ 预览包的"嵌套 zip"：artifact 是 zip 套 zip
- 现象链：从 GitHub Actions 下载的 artifact **本身是一层 zip**（upload-artifact 会把
  上传内容再压缩一遍），里面才是 `encv-preview-assets-<ver>.zip` → 导入时解压出来
  只有一个 .zip，后端只报"资源包缺文件：index.html…"，真机上根本看不出是包套了两层。
- 修两处：
  1. `.github/workflows/preview-assets.yml`：新增 **Expand zip for artifact** 步骤，
     artifact 改传**展开后的目录**（下载解压即得资源根，单层）；
     release 那份仍是单层 zip（设备端 URL 更新走它），两者都不会再套娃。
  2. `commitPreviewAssets`：缺文件且 staging 里能看到 .zip 时，报错直接点破
     "像是 zip 套 zip：请先解压外层，再导入里层的 xxx.zip"（回归锁
     `TestPreviewAssets_RejectsNestedZip`）。
- 打包形态实测（本机 zip 3.0）：`cd $ASSETS_DIR && zip -r x.zip . -x 'samples/*' ...`
  打出来是**扁的** —— 条目就是 `index.html`、`wasm/encv-container.wasm`，不套目录。
  所以"扁平化"只需保证打包时 cd 进资源目录用 `.`，不用额外处理前缀。
- ⚠️ 改 workflow 后没有 pyyaml 可用：用 `bun -e`/bun 脚本 + `Bun.YAML.parse` 校验语法，
  比肉眼读缩进可靠（bun 自带，不需要装依赖）。

### ⑤ No-NodeJS-Crypto lint 红灯：两处都是误报，修的是规则不是代码
- 命中：`scripts/skill-manager.mjs`（只 `createHash("sha256")` 算内容指纹）、
  `app/encv-preview/verify-container.mjs`（`globalThis.crypto ??= webcrypto`，
  只是给 Go 的 `wasm_exec.js` 胶水补全局对象，加解密全在 wasm 内核里）。
- ⚠️ 处理原则：**先判定用途，再决定改哪边**。这两处如果为了过门禁去删 import /
  改代码，功能就废了（skill 指纹失效、wasm 胶水在 Node 里跑不起来）。
  根因是 lint 把"导入 crypto 模块"当成"用了加密 API" —— 该改的是规则。
- 修法（关键约束）：脚本里加 `ALLOWLIST`（`路径|理由`），但**只豁免模式 A
  （node:crypto 导入）**；模式 B/C/D/E（scrypt/pbkdf2/createCipher* / encryptApiKey）
  不受豁免。已实测：在白名单文件里塞一行 `scryptSync` 仍然 EXIT=1。
  另外加了白名单腐烂检查（条目指向的文件不存在就 WARN），防止条目悄悄失效。
- 被豁免的文件会在 stderr 打 `[WARN]` → 豁免是可见、可审计的，不是静默放过。

### ⑥ 预览页在安卓上"点了没反应"：文件选择 + 浏览器打开
- 现象：预览页在应用内 WebView **加载成功**，但点「选择文件」（`<input type="file">`）
  完全无反应 —— 既不弹选择器也不报错。
- 根因：`PreviewAssetsActivity` 只设了 `webViewClient`，**没有 `webChromeClient`** →
  `onShowFileChooser` 没实现，input 的点击没有任何承接方。
  ⚠️ 这类"没反应"不要先怀疑页面：WebView 的能力是**原生侧给**的，
  缺哪个回调就少哪个能力，页面这边看不出任何异常。
- 修（三个必踩的坑，都在同一个回调里）：
  1. 取消 / 失败时**必须** `onReceiveValue(null)`，否则页面一直停在"等待选择"，
     之后点同一个 input 再也收不到回调（偶发失灵的根源）；
  2. **不能照搬页面的 accept**：那是自定义容器扩展名（.sccgv 之类），
     Android 映射不到 MIME，照搬会让选择器里一个文件都选不到 —— 用 `*/*`；
  3. Activity 销毁时也要把未回调的 callback 收掉。
  用 `registerForActivityResult`（androidx.activity 1.11 可用），不用废弃的 onActivityResult。
- 浏览器模式（用户要的"更符合应用场景"）：新增 `openPreviewAssetsInBrowser`
  → `ACTION_VIEW` 打开同一个地址。**127.0.0.1 在外部浏览器里同样是设备本身**，
  所以走的还是内嵌后端，不经过外网。
  ⚠️ 必须先用 `intent.resolveActivity()` 判空，否则没浏览器时又是一次"点了没反应"。
- 地址来源统一到 `PreviewAssetsActivity.previewAssetsUrl()`（Activity 与插件共用），
  避免端口兜底逻辑在两处各写一遍然后漂移。
- 前端 `openPreviewAssetsInBrowser()` 有 Web 回退：`isNative()` 为假时直接 `window.open`
  （dev / 当网页用时可用；非原生平台没有 GoProcess 插件，直接调会抛错）。
