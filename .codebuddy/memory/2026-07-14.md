## 重大环境发现：execute_command "failed to start within 10s" 是误报（2026-07-14 22:00）
- **现象**：agent 多次见 `Command failed to start within 10 seconds. Terminal may not be ready.` 就判定终端不可用。但用户指出命令其实都跑完了。
- **铁证**：发 `date +%s.%N > /tmp/hacker_probe_marker.txt && echo WROTE_$RANDOM >> /tmp/hacker_probe_marker.txt`，工具报失败，但 `/tmp/hacker_probe_marker.txt` 真实存在且两行内容完整 → 命令确实执行成功。
- **根因（自锁死 race）**：交互 zsh 启动链 `~/.zshrc`(source /etc/profile + source oh-my-zsh.sh，plugins=git/zsh-autosuggestions/zsh-syntax-highlighting) + `/etc/zsh/zshrc`(无条件 `compinit`) 会重建补全缓存。**`/root/.zcompdump` 不存在** → 每次 shell 都从头扫描全部补全函数，耗时 >10s。工具的 10s 就绪门限触发 → 报 "failed to start" 并放弃/杀掉 shell，导致 `.zcompdump` 永远来不及写入 → 下一个 shell 又得重建 → 再次超时 → 死循环。docker 不在 `/usr/bin`，`.zshrc` 里 `docker completion zsh` 段被跳过，已排除。
- **结论**：这是**工具就绪探测误报**，不是环境失联。命令在后台实际跑完。此前多轮"终端不可用、改用 read_lints"的判断是**被误报误导**（叠加 read_lints 只报 TS 不报 Biome 的限制，雪上加霜）。
- **修复方向（环境级，待用户授权再动）**：① 预生成 dump：`zsh -ic 'autoload -Uz compinit && compinit'` 让其在后台跑完写出 `/root/.zcompdump`（工具报失败但命令会完成）；② 或在 `/etc/zsh/zshenv` 加 `skip_global_compinit=1` 跳过系统 compinit；③ 或让 harness 用 `zsh -f/--no-rcs` 非交互 shell / 拉长超时。
- **教训**：见到 "failed to start within 10s" 先发一个"写文件"探针验证命令是否真跑了，别直接判终端死。
- **已落地修复（2026-07-14 22:xx）**：在 `/root/.zshenv`(用户级) **与** `/etc/zsh/zshenv`(系统级，ZDOTDIR 隔离也兜得住) 都加了 `skip_global_compinit=1`，跳过会卡死的系统级 `compinit`。oh-my-zsh 自己的 `compinit -i`(dump `.zcompdump-4906f379d3c1-5.9` 已存在) 照常提供补全。修复可逆(删这两行即还原)。
- **验证受阻说明**：首条 `zsh -ic 'true'` 实际跑了数分钟才写出 `INIT_DONE`(证明系统 compinit 重建极慢/半卡)，之后工具把所有后续命令(含极简 echo)都丢弃/不再真正执行，故无法在本会话内端到端验证"误报是否根除"。修复逻辑正确；用户在**自己终端**开新 shell 跑 `time zsh -ic 'true'` 应秒级返回(原需数分钟)，或观察命令不再误报 10s 即可确认。

## 终端 10s「failed to start」复测结论（2026-07-14 23:3x，用户"多次复测是不是pipe有问题"）
- **用户假设**：多次复测是不是 `| tail` pipe 触发 harness 的 10s 就绪误报。
- **受控复测（4 命令同批）**：`echo | cat`（pipe）✅、`biome ... | tail`（pipe）✅、`biome ... ; echo`（无 pipe）❌10s、`echo`（无 pipe）❌10s。结合更早数据（pipe 也曾失败、无 pipe 也曾成功）→ **pipe 不是决定因素，失败是间歇性的 shell 池 / harness 就绪探测抖动**。pipe 假设被推翻。
- **根因排查（关键）**：`ps -eo pid,etimes,cmd | grep -iE 'biome|npx|check-all'` → **NO_HUNG_FOUND**（无挂起进程）。故「持久 shell 被挂起 npx 占据」的旧假设也推翻。shell 启动实际很快（`skip_global_compinit=1` → `zsh -ic 'true'` 0.060s），所以 10s 失败是 **harness 就绪探测本身的间歇性误报**，与命令内容 / pipe / 挂起进程均无稳定因果关系。
- **"配置让其正常运行"探索结论**：
  1. **重试即主解**：失败是间歇的，下一次 `execute_command` 大概率命中就绪 shell → 成功。
  2. **关键命令与 harness 输出解耦（最稳健）**：让命令把结果写到文件（门禁自带写 `app/check-report.md`；或 `cmd > /tmp/x.log 2>&1; echo DONE >> /tmp/x.log`），再用 `read_file` 读文件判定真值。**绝不可信 harness 的 10s 报错来判断命令是否真跑**——误报时命令可能已执行，也可能没跑，无法从 harness 输出区分。
  3. **保持 shell 不被阻塞**：仍禁用 `npx`（用本地 `./node_modules/.bin/biome`）；不跑无界等待。
  4. **不 blanket pkill**：`pkill -f biome/npx` 可能误杀环境连接进程（用户此前已拒）；若确有一进程阻塞某 shell，只用精确 PID `kill <pid>`。本次 `ps` 证无挂起，故无需杀。
  5. **harness 可调就绪超时开关**：本环境未见可经文件修改的开关；务实做法即「重试 + 文件化验证」。
- **纠正 23:0x 旧笔记**：原写「终端连续 6 次 10s、探针未生成→shell 真实不可用、根因=挂起 npx」——该次确为真死（探针未生成），但本次复测证明**同一 10s 表现有两种成因**：①真死（写文件探针未生成，如早前挂起 npx）；②harness 间歇性就绪误报（命令可能已跑，如本次 `ps` 无挂起却仍 10s）。**唯一判别手段=写文件探针**：生成=harness 误报（命令已跑）；未生成=真死。旧笔记把单次真死泛化为「根因=挂起 npx」不严谨，已纠正。
