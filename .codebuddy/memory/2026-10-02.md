## 1. 【核心】共享文件句柄被"私自"关闭 + 引用计数不配平（并发必现）

**现象（真机通路实测）**：
- 小文件（44KB）并发 4 路 Range：**约 25% 的请求失败** —— 客户端收到
  19 字节 `Seek Not Supported`（416），或 **500**（后端 panic）。
- 大文件（8.6MB，走流式分支）并发 3 路：**约 3/24 条响应被截断**
  （HTTP 206，但实体体只有 327680 / 196608 / 884736 字节）。
- 后端日志同时刷屏：
  `WARN: [fileContainerReader] Failed to close initial main file handle: ... file already closed`
  `WARN: [ContentHandler.ServeFile] Stream to client was interrupted ...: file already closed`

**根因链（读代码 + 日志取证）**：
1. `globalFileHandlePool.Get(path)` 返回的是**按路径全局共享**的同一个 `*os.File`（引用计数）。
2. `fileContainerReader.Close()` 却直接 `initMainFileHandle.Close()`，**绕过池** ——
   把别的 reader 正在用的同一个 fd 关掉（并发下 ⇒ 别人读失败）。
3. `GetFragmentReader` 复用 init 句柄时返回 `readOnlySectionCloser`（Close 什么都不做），
   于是"取引用"和"还引用"**不配平**。
4. 上层还有一处**重复 Close**：`serveEncryptedFile` 里 `defer decryptReader.Close()`
   与 `defer prov.Close()` 会关同一个 decryptReader 两次；`SequentialSeekableDecryptReader.Close()`
   不幂等 ⇒ 第二次又把池的引用计数**多减一次** ⇒ fd 在别人还在读时被提前关闭。

**修复**（4 处，均在本次）：
- `internal/v2/reader/file_container_reader.go`
  - `Close()` 改为 `globalFileHandlePool.Put(initMainFileHandle)`（归还，不再直接 Close）。
  - `acquireMainFile()` 只负责"容器级"引用；`GetFragmentReader` 每次使用**再 Get 一次**，
    由返回的 wrapper 在 Close 时 Put —— 两条引用互不干涉，配平。
  - 主文件不再返回 `readOnlySectionCloser`（内存源 `r.src != nil` 分支仍保留）。
- `internal/v2/reader/sequential_seekable_reader.go`：`Close()` 加 `closed` 标志，**幂等**。
- `internal/server/server_handle.go` / `internal/service/mobile_service.go`：
  provider 接管后**只** `defer prov.Close()`，删掉重复的 `defer decryptReader.Close()`
  （创建 provider 失败的分支里自己关，避免泄漏）。

**回归锁（先红后绿已验证）**：`internal/v2/reader/container_handle_lifecycle_test.go`
- `TestFileContainerReader_CloseMustNotBreakOtherReaders`（确定性）：关一个容器 reader 后，
  同进程其它 reader 必须仍能读。修前 `read ...: file already closed` → 红。
- `TestSequentialSeekableDecryptReader_CloseIsIdempotent`：用**池引用计数**白盒断言
  "第二次 Close 不得再减引用"（共享 fd 被提前关闭只在并发下才显现为读错误，
  直接断言读错误会漏）。修前红（`git stash` 撤掉修复实测 FAIL，还原后 PASS）。
- `TestDecryptReaderFactory_ConcurrentReadersSameContainer`（8 并发 × 3 轮，小文件缓存分支）
- `TestDecryptReaderFactory_ConcurrentReaders_LargeStreamedContainer`（4MB → 流式分支，4 并发 × 2 轮）
- `TestFileContainerReader_CloseIsIdempotent`

**真机复验**：重编 x86_64 后端 → 大文件并发压测 **8 轮 × 3 路 × 3 次 = 72 条，0 失败**
（修前同脚本 3/24 失败）；后端日志 `file already closed` 计数归零。

## 2. provider 交不出 reader ⇒ nil 解引用 panic（500）

- `LocalFileProvider.GetReader()` 在 `loadErr != nil`（解密/读失败）时**返回 nil**，
  `ContentHandler.ServeFile` 直接 `io.Copy(w, io.LimitReader(nil, n))` ⇒ nil pointer dereference。
- 真机证据：模拟器后端日志 `panic recovered: runtime error: invalid memory address`
  栈在 `content.go:95`（io.Copy），GIN 记 500。
- 修：`content.go` 开头 `reader == nil` → 显式 500 并记 ERROR。
- 回归锁：`internal/v2/handler/content_range_bounds_test.go::TestServeFile_NilReader_Returns500WithoutPanic`
  （修前 `require.NotPanics` 实测失败，栈同上）。

## 3. 416 带满实体体 + 缺 `Content-Range: bytes */size`

- `parseRangeHeader` 判定 416 时把 start/end 重置成"全文件"，`ServeFile` 照常 io.Copy ⇒
  客户端收到 **416 + 整个文件的实体体**（白解密 + 白传全量），且没有 RFC 7233 要求的
  `Content-Range: bytes */<size>`。
- 真机证据：44KB 样例发 `Range: bytes=449660-` → 416 且实体体 44966 字节。
- 修：`content.go` 统一 416 出口 `write416()`：设 `Content-Range: bytes */size`、
  `Content-Length: 0`、只 WriteHeader 不写实体体；三处 416 分支（越界 / start>end /
  不可 seek / SeekTo EOF）全部收敛到它。
- 回归锁：`content_range_bounds_test.go` 两条（越界、反向区间），修前红。

## 4. HEAD /stream → 404（且修完头后仍会白解密全文件）

- 修：`routes.go` 加 `r.HEAD("/stream")` / `r.HEAD("/decrypt")`；

## 5b. 【已修 · 决策 A】损坏的容器 → 静默乱码（缺陷 #5）

**真机复现**：把合法容器中间 512 字节抹成 0，`/stream?path=...` 返回
**HTTP 200 + 长度 44966（与明文完全一致）+ 内容从第 25496 字节起是乱码，且全程不报错**。
（脚本：`scripts/emu-backend-failpath.sh` 第 2 项，当前红。）

**根因（已取证，不是猜）**：
- `go run ./cmd/encv manifest-v2 <容器>` 显示 fragment 的 `data_crc32 = 0`，
  且 v4 未启用 HMAC ⇒ 容器里**根本没有完整性元数据**，读取端无从校验。
- `fileContainerReader.GetFragmentReader` 里唯一那份 `verifyFragmentAt`（CRC 校验）
  被 `if r.headerVersion != 4 { ... }` 排除 ⇒ **v4 容器一律不校验**。
- 但 KVI 里其实带着 `original_file_md5`（明文 MD5）—— 有人有，没人用。

**为什么不能擅自动**：修法涉及**容器写入格式的默认行为**（契约变更），需要产品/架构决策：
- A. 写入端默认启用 HMAC（最彻底，但影响所有新产出的容器 + 兼容性评估）
- B. 读取端让 v4 也走 fragment CRC（前提是容器带 CRC，对存量无效）
- C. 读取端用 KVI 的 `original_file_md5` 做后置校验（只覆盖全量读：下载 / ≤3MB 缓存分支；
  流式播放"边下边播"时才知道坏了，能做的是记 ERROR + 前端提示）

**用户决策：A（写入端默认启用完整性校验）。已实施 —— 但要如实说明落地形态**：

视频/主链路（`encrypt-v2`）走的是 **v4 fragment 栈**（`SingleFileContainerWriterV4`），
不是 `writer.WriteV4ContainerTo` 那条 segment 栈（那才有 `EnableHMAC` 开关）。
所以"A"在这条产线上落地为**写入端写入可校验的 CRC32 元数据 + 读取端默认校验**：

| 改动 | 文件 |
|---|---|
| v4 分片累计并写入真实 CRC32（修前写死 0） | `internal/v2/writer/single_file_container_writer.go` |
| v4 manifest 新增 `data_crc32` 字段并写入（omitempty，缺省 0） | `internal/v2/types/segment_v4.go` + 上面同文件 `writeManifestV4` |
| `AdaptV4ToV2` 把 segment 的 CRC 带到 fragment（修前硬编码 0） | `internal/v2/container/handle/adapter.go` |
| 读取端边读边校，不符 → `types.ErrDataCorrupted` | `internal/v2/reader/crc_guard_reader.go`（新）+ 两个 decrypt reader 接入 |

**两个必须记住的实现细节**（都踩过）：
1. `verifyFragmentAt` 是读 **v2 BlockHeader** 的，v4 数据区是裸密文，用不上；
   所以 v4 只能"边读边算 CRC"，不能"打开时校验"。
2. **必须在"读满整片"时判定，不能只等 `io.EOF`**：HTTP 侧是
   `io.Copy(w, io.LimitReader(reader, contentLength))`，contentLength 正好等于明文长度时
   LimitReader 读满即停，**不会再调底层一次** ⇒ 底层那次 `(0, io.EOF)` 永不发生 ⇒
   只等 EOF 判定的话，**大文件（流式分支）的校验永远不触发**，后端还会若无其事记一条
   "Successfully served N bytes"（8.6MB 样例实测）。回归锁：
   `TestCRCGuard_DetectsMismatchWithLimitReader`。

**验证（真机 + 单测）**：
- 单测先红后绿：`TestV4Fragment_WriterRecordsDataCRC32`（修前 `DataCRC32 = 0`）、
  `TestV4Fragment_TamperedData_MustFail`（修前"静默解出 4800 字节乱码且不报错"）；
  撤销写入端改动实测两条都 FAIL，还原后 PASS。
- 真机（模拟器内后端）：损坏的小容器 → **500 显式失败**（修前 200 + 乱码）；
  损坏的大容器（流式分支）→ 后端日志 `数据完整性校验失败（CRC32 期望 cc3f0abf，实际 679957a0）`
  且不再记 Successfully served；**存量老容器（无 CRC）仍 200 + 全量字节一致**（向后兼容）。
- 闸门：`emu-backend-failpath.sh` **10/10 PASS**（新增 --legacy / --big 两项）。

**遗留局限（如实记录）**：
流式分支的 CRC 要到"读完整片"才知道 ⇒ 字节已经发给客户端了，HTTP 层仍是
`200 + 全量长度 + 乱码`（后端知道，客户端不知道）。
想让**播放/下载**侧也立刻失败，需要**分块 CRC**（每 64KB 一块，读到就校）——
这是又一次容器格式扩展，等下次决策再动。

## 5e. 【已修】分块 CRC（决策 A 的第二半：让流式播放也能"早期发现"损坏）

- 为什么还要做：整片 CRC 要**读完整片**才知道坏了 —— 8.6MB 实测：HTTP 仍是
  `200 + 8606376 字节全量乱码`，只有后端日志知道（"已读 8606376/8606376"）。
- 修法：写入端每 **64KB** 落一个块 CRC（`Fragment.BlockCRCSize/BlockCRC32`，
  经 `Segment_v4` 同名新字段由 `AdaptV4ToV2` 搬到 fragment）；读取端
  `crcGuardReader.feedBlocks` 每读满一块就比对，不过立即报 `ErrDataCorrupted`。
- 兼容：块大小 0 / 列表空（老容器）⇒ 退化成整片校验，行为不变。
- 元数据体积：8.6MB → 132 块（约 0.5KB）；1GB 电影也才约 64KB。
- 先红后绿：关掉分块 CRC 后实测
  - `TestV4Fragment_BlockCRC_Written`：`BlockCRCSize=0 块数=0` → 红
  - `TestV4Fragment_BlockCRC_DetectsEarly`：`发现得太晚：报错时已读 524280/524280` → 红
- **真机验证（关键数字）**：篡改 8.6MB 容器中点后，客户端只收到 **4,325,376 字节**
  就在损坏块边界被中断（修前是 8,606,376 全量）；后端日志
  `第 N 个数据块（起点 4259840，65536 字节）完整性校验失败`。
- 闸门：`emu-backend-failpath.sh` 第 6 项新增"早期发现"断言（解析日志里的"起点 S"，
  要求 S < 文件一半）→ **11/11 PASS**。
- ⚠️ 遗留：HTTP 状态码仍是 200（头已经发出去了），只是**实体体被截断**。
  播放器会看到"流提前结束"而不是 5xx。要让状态码也正确，得在吐第一个字节前
  预校验（=再读一遍整片，本地文件可行、远程/alist 流不可行）——未做。

## 5f. 【已修】segment 栈（compose / wasm 路径）默认开启 HMAC

- 修前两处洞：① `Options.EnableHMAC` 是 bool，零值 false ⇒ 不显式设就不开；
  ② `EncryptBytes`（整块路径）**压根没把 EnableHMAC 传给 writer**，即使 Options 要求开，产物也不带 MAC。
- 修：三态（`EnableHMAC` / 新增 `DisableHMAC`）+ `withDefaults()` 默认开启 + 整块路径补传。
- **连带发现的真 bug**：开了 MAC 后，读取端（`AdaptV4ToV2`）用 manifest 的 `Size`
  反推数据长度时**没扣 MAC 字节** ⇒ 5100 字节明文解出 **5110 字节**（尾部多 10 字节垃圾）。
  修：新增 `Segment_v4.MacSize` 字段（writer 回填 10），adapter 扣掉。
- **另一条连带修复**：`WriteV4ContainerTo` 之前只把 CRC 写在磁盘 SegmentHeader 上，
  manifest 里没有 ⇒ fragment 栈读取路径看不到 ⇒ 补上 `Segments[i].DataCRC32` 回填。
- 先红后绿：撤掉"默认开启"后 `TestComposeV4_Defaults_EnableHMAC` 红；
  （`TestComposeV4_TamperDetectedByDefault` 即使不开 HMAC 也是绿的 —— 因为 CRC 回填
   已经能检出篡改，这是**预期内**的冗余保护，不是测试失效。）
- 遗留：**MAC 在 fragment 栈读取路径上并不被校验**（只有 `segment_reader` 那条栈校验）。
  所以 segment 栈容器的篡改实际上是被 **CRC** 发现的，不是被 MAC 发现的。要不要让
  fragment 栈也校验 MAC，属于下一个待决策项。

## 5g. 【已修】吐字节**之前**的完整性预校验 ⇒ 损坏文件返回 422（而不是 200 + 截断流）

- 为什么还要它：分块 CRC 只能在读到损坏块时中止，那时 `200 + Content-Length`

## 12f. P2b 二维码 UI 的两个硬坑（长期）

- **⚠️ `@vite-ignore` + 裸说明符 = 运行时炸**：`import(/* @vite-ignore */ "qrcode")` 会**阻止 Vite 预打包**，浏览器运行时 `Failed to resolve module specifier 'qrcode'`。动态 import 裸包名**不要加** `@vite-ignore`（那是给运行时拼接的变量路径用的）。

## 12j. P3.4 远端读通道 + 两个环境/编码坑（长期）

- **P3 搜索页接入**：`useFilesView` 新增**可选** `peerSearch` 注入 → `peerHits`（**独立容器，绝不混进 `searchResults`/`displayFiles`**）；Files.vue 展示区「来自已配对设备（N）」+ `PeerSourceBadge` + 「在线打开」。
  - ⚠️ **UI 位置坑**：展示区若放在搜索 banner 之后会落进 `v-if="(loading||…||displayFiles.length===0)"` 的 **v-else 分支** ⇒ 本端 0 命中时整块消失。必须放在空态判断**之前**，并把空态条件改成 `displayFiles.length===0 && peerHits.length===0`。
- **⚠️ 不要对整个包跑 `gofmt -w`**：我曾格式化 `internal/server` 全包 → 28 个无关文件 ~500 行 churn（Go1.19 注释规范化）。确认方法：`git diff -w --stat` + 抽样 diff；确认纯格式后按文件还原。**只对自己改的文件跑 gofmt**。

## 13. Capacitor 桌面端调研（用户质疑后补做，长期有用）
