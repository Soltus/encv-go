## 2. APK 构建在本机的两个坑（都已在会话内解决）

- **repo.maven.apache.org / repo1.maven.org 对容器出口 IP 限流（HTTP 429）**：
  Gradle 解析依赖时在 `ErrorHandlingModuleComponentRepository.tryResolveAndMaybeDisable` 里
  重试+sleep（jstack 取证），表现为"卡住"十几分钟不报错。
- ⚠️ **大教训：`settings.gradle.kts` 是 `RepositoriesMode.PREFER_PROJECT`** —— init script 一旦给
  project 注入任何仓库（哪怕只是加一个镜像），settings 里那一整串
  （google() + 各镜像 + `com.github.*` 走 jitpack 的 `exclusiveContent`）就被**完全忽略**，
  表现为 androidx.* 全部 "Could not find"（只搜注入的仓库）。
  正确做法：init script **只 rewrite URL、绝不 add 仓库**（见 `/root/.gradle/init.d/mirrors.gradle`）。
- 另一个坑：腾讯云 nexus 镜像会**代理 jitpack 的 pom 但没有二进制**，导致
  `com.github.getActivity:Logcat` 停在 "Could not find Logcat-13.0.jar"。项目自己的
  `exclusiveContent`（com.github.* 只走 jitpack）就是为此写的，别用腾讯 nexus 兜底。
- Gradle daemon 崩过一次（`-Xmx4g` + 模拟器同跑内存吃紧），用 `-Dorg.gradle.jvmargs=-Xmx3g` 过。

## 6. 「宿主性能足够」为什么仍然失败 —— 模拟器性能根因量化（对照实验）

对照组（决定性）：**系统自带 `com.android.settings/.Settings` 启动 `Status: timeout`、`WaitTime: 47034ms`**。
纯系统应用、零业务代码都启动超时 ⇒ 失败与 app 代码/配置无关，是模拟器整体太慢。

CPU 量化（同一个 20 万次 shell 循环）：
- 宿主（x86_64 原生）：**418 ms**
- 模拟器内（x86_64 系统跑在 QEMU TCG 上，扣掉 747ms adb 往返）：**≈ 37.3 s** ⇒ **约 90× 慢**

结论链：
1. 根因是**没有 KVM**（`/dev/kvm` 不存在、CPUID 无 vmx/svm、无嵌套虚拟化）→ 只能 QEMU TCG 软件翻译。
   宿主 CPU/内存再多也只能把这个常数倍缩小一点，**架构性开销无法用资源堆叠消除**。
2. 第二层：app 是 arm64-only（`lib/arm64-v8a/libencv-go.so` 49MB），在 x86_64 系统上还要叠
   `libndk_translation`（ARM→x86 二进制翻译）——TCG 之上再叠一层。
3. 表现：Zygote fork + ART 初始化 + dex 加载 > 10s → `failed to attach` → `Killing … start timeout`；
   把 `activity_start_timeout` 放宽到 300s 后 app 起来了，但 **SystemUI 自己先 ANR**（同为 TCG 慢）。
4. 附带现象：模拟器被 kill -9 后 `pm list packages` 里 encvgo 消失（userdata 未落盘）→
   `am start -W` 报 "Activity class does not exist"；重装代价 4 分钟 dexopt（安装慢本身也是 TCG 表现）。

可行的改进方向（按性价比）：
- **唯一根治**：让宿主/平台把 `/dev/kvm` 挂进开发容器（Dockerfile 无法声明设备挂载，需 CNB 平台侧能力）。
  有 KVM 后启动从分钟级降到秒级。
- 减轻负担：AVD 改 `-cores 2 -memory 2048`（TCG 多线程同步开销有时反而更大）、换 `aosp_atd` 系统镜像（组件少）。
- 务实替代：**不依赖 UI 交互**做验证（adb shell + 后端 HTTP，或宿主机真实浏览器 + 真实后端）——
  本次"加密视频预览"就是用这条路拿到证据的。

## 7. CNB 平台侧能力查证（能否拿到 KVM / 换架构来救模拟器）

**官方构建节点（docs.cnb.cool/zh/build/build-node.html）**：
- `cnb:arch:amd64`（1~64 核，默认 8）、`cnb:arch:arm64:v8`（1~16 核）
- `cnb:arch:amd64:gpu` / `:gpu:L40`（固定 16 核、48GB 显存）
- `runner.tags` 对**云原生开发（vscode 事件）同样有效**（文档示例即用 gpu 节点）
- 自托管 Runner：支持 Linux，但**仅 arm64**，且**不支持云原生开发**（只能用于云原生构建）
- 没有 privileged / devices / `/dev/kvm` 的声明式能力；本容器 docker service 是
  **rootless + no-new-privileges**（`docker info` SecurityOptions），连 `--device` 都做不了

**本机硬事实（复核）**：
- CPU 是真 **AMD EPYC 9K65**（硬件支持 AMD-V/SVM），但 CPUID **不暴露 svm**、带 `hypervisor` 标志
  → 宿主虚拟化层**未开启嵌套虚拟化**；无 `/dev/kvm`、无 kvm 内核模块

**两条"架构路线"都被证伪**：
1. amd64 官方节点：有硬件能力但没开 nested virt，KVM 拿不到（需平台侧开通，企业版/管理员）
2. arm64 节点：① 官方 **Android Emulator 只有 linux x86_64 构建**
   （repository2-1.xml 里只有 `emulator-linux_x64`，没有 aarch64）→ arm64 Linux 上跑不起来；
   ② 自托管 arm64 主机又不支持云原生开发

**结论**：CNB 架构能力确实存在（可选节点/架构），但**恰好不覆盖"给开发容器嵌套虚拟化"**。
模拟器加速在当前公开能力下无解；无 KVM 时 UI 级真机测试不可行（Settings 启动 47s 超时为证）。
降级路线：Robolectric/单测（纯 JVM）+ 容器内跑 arm64 原生二进制 + **宿主机真实浏览器 + 真实后端**
（本次"加密视频预览"取证就是走这条）。

## 8. 无 KVM 模拟器跑主应用 —— 三层根因逐层剥开（2026-10-01 晚，全部实测）

**第一层：ANR（已修，两个真实产品 bug）**
- `EncvGoService`：`startForeground` 藏在 `onStartCommand → worker.execute → startGoProcess`
  里（后台线程池），慢环境下超 20s 义务 → "did not then call Service.startForeground()" ANR。
  修：`onStartCommand` 主线程第一行立即 `startForeground(NOTIFICATION_ID, buildNotification("后端启动中"))`。
  ⚠️ 顺带证伪：`activity_manager_constants` 的 `service_start_foreground_timeout_ms` 放宽**无效**。
- `com.hjq.logcat.LogcatService`：manifest meta-data `LogcatNotifyEntrance=true` 会让库**自启 FGS**，
  慢环境 onCreate 超时 → 同类 ANR。修：`LogcatNotifyEntrance=false`（应用内日志已由 LogBridge 承担）。

**第二层：dex 未 AOT（已解）**
- 安装后直接启动 → ART 运行时解释/JIT → attach 超时被杀。
  修：`adb shell cmd package compile -m speed -f com.encvgo.app`（85s）。
  效果量化：`Settings` 启动 47s 超时 → **489ms**。此前"TCG 不可用"的判断是这个假象导致的。

**第三层：Berberis（ARM→x86 翻译器）崩溃（当前阻塞）**
- app 过了 ANR 关后，主线程 `Fatal signal 5 (SIGTRAP) SI_KERNEL`、`pc=0`、寄存器全 0、
  栈全在 `oat/x86_64/base.vdex` → Berberis 与 ART/AOT 交互崩溃，非业务代码。
- 正在验证的绕过：**arm64 系统镜像**（`system-images;android-36;google_apis;arm64-v8a`）——
  emulator linux-x64 包自带 `qemu-system-aarch64`，x86_64 宿主模拟器可跑 arm64 guest，
  app 是 arm64 原生 → 完全不走 Berberis。代价：TCG 模拟 arm64 guest 更慢，但正确性优先。

**已固化的"模拟器可用性"前置步骤（供 emuctl 后续吸收）**：
```
adb root
settings put global activity_manager_constants "activity_start_timeout=600000,service_start_foreground_timeout_ms=600000,service_timeout=300000,input_dispatching_timeout=180000,broadcast_timeout=180000,content_provider_timeout=180000"
svc wifi disable; svc bluetooth disable; settings put global wifi_scan_always_enabled 0
setprop persist.log.tag W; setenforce 0
adb install -r app.apk && adb shell cmd package compile -m speed -f com.encvgo.app
```

## 9. x86_64 ABI 构建（消掉 Berberis 的正确做法）+ 剩余崩溃

**做法**：`build_go_binary` 只有 `GOARCH=arm64`；照同样的 CGO+NDK 方式编一份 amd64：
```
CC=$NDK/toolchains/llvm/prebuilt/linux-x86_64/bin/x86_64-linux-android24-clang
CGO_ENABLED=1 GOOS=android GOARCH=amd64 CC=$CC go build \
  -o app/encv-mobile/android/app/src/main/jniLibs/x86_64/libencv-go.so ./cmd/encv-mobile
```
`build.gradle.kts` 的 `ndk.abiFilters` 原本写死 `arm64-v8a`（x86_64 的 .so 会被丢掉）→
改为 `EMU_X86_64=1` 时追加 `x86_64`（默认 arm64-only，release 体积不变）。
验证：`pm dump` 显示 `primaryCpuAbi=x86_64` —— app 在模拟器上**完全原生、不进 Berberis**。

**剩余崩溃（未解决）**：x86_64 原生下主线程仍 `Fatal signal 5 (SIGTRAP) SI_KERNEL`，
崩溃前紧邻 `F/crashpad ... -----BEGIN/END CRASHPAD MINIDUMP-----`（Chromium/WebView 的崩溃捕获器），
且 tombstone 不生成（ART 主动 abort）。已证伪的方向：
- arm64 系统镜像：emulator 直接拒绝（"CPU Architecture 'arm64' is not supported on x86_64 host"）
- `MainActivity android:hardwareAccelerated="false"`：无效（已还原，别留）
- 放宽 `service_start_foreground_timeout_ms` 等 AM 常量：对 startForeground 类 ANR 无效
下一步候选：WebView 版本/实现（换 Android System WebView 或关闭其 GPU 路径）、
`aosp_atd` 系统镜像（组件更少）、或在 `Application.onCreate` 里延迟 WebView 初始化。
