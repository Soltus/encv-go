# 插件生命周期与可选能力契约

> 适用范围：`internal/v2/plugins`（v2 插件注册表）与 `pkg/encv/plugins`（对外 API）。
> 动机：借鉴 Cordis（Koishi / DeepSeek Harness 的插件内核）的两条性质——
> **副作用可逆** 与 **生命周期包含**。完整 IoC/DI 容器不引入（见文末「不做什么」）。

## 1. 生命周期状态机

每个插件在注册表里有一个可观测状态（`internal/v2/plugins/lifecycle.go`）：

| 状态 | 含义 |
| --- | --- |
| `pending` | 已声明，尚未开始初始化 |
| `loading` | 正在执行 `Initialize` |
| `active` | 初始化成功，可用 |
| `failed` | 初始化或卸载失败（附带 `error` 文本） |
| `disposing` | 正在卸载 |
| `disposed` | 已卸载，副作用已回收 |

读取方式：

```go
plugins.GetPluginStates()               // 全量快照（副本）
plugins.GetPluginState("video")         // 单个
```

## 2. 初始化：失败隔离

`InitializeAll(ctx, list)`（以及全局入口 `InitializePlugins`）的语义：

- **单个插件失败只把它自己标记为 `failed`，不拖垮其余插件**——与既有容错哲学一致
  （`pkg/encv/plugins.InitializeWithSettings` 也是「失败插件被禁用，服务照常启动」）。
- 错误用 `errors.Join` 聚合返回；调用方可忽略（拿一部分可用插件）也可整体失败。
- 每条初始化路径都要登记状态。`pkg/encv/plugins.initializeSinglePlugin` 这类绕过
  `InitializePlugins` 的路径，必须自己调 `SetPluginState`，否则状态表会缺项。

## 3. 卸载：严格逆序 + 可选能力

`DisposeAll(list)` / `DisposePlugins()`：

- **逆序执行**：后装载的插件可能依赖先装载的插件，先卸载依赖方才能保证
  「提供方比消费方活得久」（生命周期包含）。
- 只有实现了 `Disposable` 的插件才被真正回收；未实现的插件仅标记为 `disposed`，
  **不报错**（渐进式改造，不强求一次到位）。
- 某个插件 `Dispose` 失败不会中断其余插件的卸载，失败者标记为 `failed` 并带上错误。
- 返回值按**入参顺序**排列（执行顺序是逆序），便于调用方按插件列表读取结果。

```go
type Disposable interface {
    // 回收临时目录、子进程、连接池、wasm worker 等副作用；必须幂等。
    Dispose() error
}
```

## 4. 可选能力：消灭「特权核心」

调度层不再 import 具体插件包、不再写 `if vp, ok := plugin.(*video.VideoPlugin)`。
改为只问「你有没有这个能力」（`internal/v2/plugins/interfaces/interfaces.go`）：

| 可选接口 | 用途 |
| --- | --- |
| `OutputDirSetter` | 需要知道本次任务输出目录的插件 |
| `PostEncryptVerifySetter` | 加密完成后做一次自检 |
| `EncryptedSourceProvider` | 暴露预处理中间产物路径，由调度层统一清理 |

适配函数在 `internal/v2/plugins/capabilities.go`：`applyOutputDir` /
`applyPostEncryptVerify` / `cleanupPreprocessedSource`（清理前有三重安全判断：
路径非空、不是输入文件本身、必须位于 `.encv_tmp` 目录）。

守卫测试 `TestRegistry_DoesNotSpecialCaseConcretePlugins` 会扫描 `registry.go`，
一旦发现对具体插件类型的断言/分支（`.(*video.` 等）立即失败。
注意：装配列表里出现 `&video.VideoPlugin{}` 是**合法**的——装配 ≠ 特判。

## 5. 对外 API（`pkg/encv/plugins`）

```go
InitializePlugins(ctx) error            // 装载（状态登记 + 失败隔离）
DisposePlugins() []PluginStatus         // 逆序卸载，返回每插件最终状态
GetPluginStates() []PluginStatus        // 状态快照，供 /api 排障
```

宿主应在**退出进程**或**重载插件配置**时调用 `DisposePlugins`。

## 6. 不做什么

- **不引入 IoC/DI 容器**：ENCV 插件是编译期装配、进程内长驻，依赖注入容器的收益
  远小于其复杂度。
- **不把 `Dispose` 塞进 `Plugin` 胖接口**：那样 7 个插件必须一次全改才能编译。
  用可选接口逐个改造。
- **暂不做 `Requires()/Provides()` 依赖声明**：等真的出现「插件依赖插件」再引入，
  届时装载顺序由拓扑排序决定，而不是现在的切片顺序。

## 7. 已落地的实现

### video 插件（`internal/v2/plugins/video/dispose.go`）

`VideoPlugin.Dispose()`：

- 删除 `outputDir` 下 ENCV 自建的两类临时目录：`.opencv_tmp`（预处理中间产物）与
  `.opencv_verify_*`（加密后自检目录）；**其余产物一律不动**（容器、字幕导出目录等）。
- 复位任务态：`inputPath` / `encryptedSourcePath` / `splitSets` / `splitPartPaths` /
  `isPostEncryptVerify` / `lastVerifyWarnings`，避免插件实例在下次任务里串味。
- 幂等；`outputDir` 为空或不存在都不报错。

> 说明：ffmpeg / mkvmerge 目前都是同步 `cmd.Run()`，没有长驻子进程需要跟踪，
> 所以 Dispose 不做进程回收。将来若引入后台转码进程，应在此处登记并 terminate。

### 停机接线

`internal/server.(*Server).Stop()` 在 HTTP `Shutdown` **之后**调用
`plugins.DisposePlugins()`（顺序不能反：否则还有请求在用插件），
逐个插件回收并把失败者以 WARN 记日志。

## 8. 对外可观测性：`/api/plugins`

每个插件额外下发三个字段（后端 `internal/server/mobile_metadata.go`）：

| 字段 | 说明 |
| --- | --- |
| `state` | 生命周期状态；从未登记过的插件按 `pending` 上报 |
| `error` | 初始化/卸载失败原因，正常时为空 |
| `disposable` | 是否实现了 `Disposable`（停机时能否被统一回收副作用） |

前端类型在 `app/packages/shared-components/src/api/encv_plugins.ts`：
`PluginState` 联合类型 + `PluginMeta.state/error/disposable`。
三个字段在 TS 里标为**可选**——后端总是下发，但既有测试夹具只填业务字段，
标必填会打断 `check:all` 的类型检查门禁。
