# 03 · 能力边界与已知坑

> 每条都带 2026-09-18 在 `/workspace` 的复现方式与实测证据。

## 1. 头号陷阱：单 root 工具 × 多 root 配置

### 1.1 现象（红）

注册为 `CODEMOGGER_ROOT=/workspace`、而工作区存在 `.codemogger.json`（6 个 root）时：

| 工具 | 实测返回 |
|---|---|
| `list` | `No files indexed. Run codemogger index <dir> first.` |
| `references useTaskStore` | `No imports found for: useTaskStore` |
| `related useTaskStore` | `no codebase indexed at /workspace/.codemogger/index.db — run codemogger_index first` |

而同一时刻**各 root 的库都是好的**（多 root 索引已完成）；`search` / `grep` / `leaks` 全部正常。

### 1.2 根因

`lib/config.mjs` 里 `DB = join(ROOT, ".codemogger", "index.db")`，
`references`/`context`/`impact`/`leaks`/`list`/`related` 全部钉这一个库。

### 1.3 为什么这个库永远建不出来

shim 的 `index` 分支：

```bash
if [ "$SUBCMD" = "index" ]; then
  if [ -n "$ROOTS_TSV" ]; then          # ← .codemogger.json 有 roots 就恒为真
    # 循环各 root，各自 <root>/.codemogger/index.db
  fi
fi
```

实测（两层都能复现）：

- CLI 层：`bash codemogger-shim index /workspace --db /workspace/.codemogger/index.db`
  → 输出 `== multi-root index (from workspace/.codemogger.json) ==`，dir/db 被忽略。
- MCP 层：`codemogger_index{dir:"/workspace/app/preview-gateway"}`
  → 同样打印六 root 的循环，**没有只索引 preview-gateway**。

（`codemogger_index` 工具内部是 `runShim(["index", args.dir || ROOT], { db: false })`，
参数是传给了 shim 的，只是被多 root 分支吞掉了。）

⇒ 只要 CONFIG 里配了 roots，`ROOT` 指向的单一库就无法通过 MCP 工具刷新。

### 1.4 正确做法（实测转绿）

把注册的 `CODEMOGGER_ROOT` 指向**一个真实被索引的 root**：

```jsonc
{ "command":"node", "args":["/scripts/codemogger-mcp/index.mjs"],
  "env": { "CODEMOGGER_ROOT": "/workspace/app/encv-mobile" } }
```

同一查询立刻有数据（`references useTaskStore` → 5 条；把共享包库拷到钉定路径后
`related` → nodes=12/edges=124）。`search`/`grep` 的多 root 覆盖**不受影响**。

**给镜像项目的建议**：`register.mjs` 增加一步「存在 `.codemogger.json` 时，把 `CODEMOGGER_ROOT`
默认设为 weight 最高的 root」，或给 shim 增加 `--single-root` 逃生开关。

### 1.5 最终采用：把钉定的单库填上（实测可行，且结果更完整）

保留 `CODEMOGGER_ROOT=/workspace`，**绕过 shim 直接调 CLI** 把单库建出来
（shim 会吞掉 dir/db，裸 CLI 不会）：

```bash
node /usr/local/lib/node_modules/codemogger/dist/cli.mjs index /workspace \
  --db /workspace/.codemogger/index.db
```

实测：约 **10 分钟**成库（2612 files / 21924 chunks，~89MB），之后
`list/references/context/impact/related` 在该实例上立刻读到数据。
而且结果**比单前端库更完整**（同一实体跨仓库的引用都在一张图里）：

| 查询 | ROOT=app/encv-mobile（单前端库） | ROOT=/workspace（整仓单库） |
|---|---|---|
| `references useTaskStore` | 5 | **9**（多出 shared 包内的 4 个消费者） |
| `impact @/api/encv` | 132 | **287** |
| `related useTaskStore` seed 解析 | 5 | **10**（含 `src/stores/taskStore.ts` 定义节点） |

代价与注意事项：

- 与各 root 的库重复一份；**刷新必须用同一条裸 CLI 命令**（MCP 的 `index` 刷新不了它）。
- 建库期间读请求会报 `Error: database is locked`（实测），属正常，等建完即可。
- 新容器里这个库不存在 ⇒ CI 里加一步「已存在则跳过，否则后台 nohup 建库」即可自愈。

> 若不想维护这份重复库，退回 §1.4 的「ROOT 指向某个已索引 root」也完全可用，
> 且能被 MCP `index` 自然刷新——两条路的取舍就是**跨仓库完整度 vs 自维护性**。

若希望保留 `CODEMOGGER_ROOT=/workspace`（跨仓库统一引用图），可以**绕过 shim 直接调 CLI**
把它建出来（shim 会吞掉 dir/db，裸 CLI 不会）：

```bash
node /usr/local/lib/node_modules/codemogger/dist/cli.mjs index /workspace \
  --db /workspace/.codemogger/index.db
```

实测：后台执行约 3–6 分钟成库（~45MB 量级），之后 `list/references/context/impact/related`
在该实例上立刻读到数据，无需等客户端重启（`DB` 路径不变，只是库从空变有内容）。
代价：与各 root 的库重复一份；且**刷新必须用同一条裸 CLI 命令**（MCP 的 `index` 刷新不了它）。

## 2. 索引是快照，且默认不自动刷新

- shim 默认 `CODEMOGGER_NO_AUTOINDEX=1`（`lib/config.mjs` 的 `NO_AUTOINDEX` 逻辑镜像实验版）。
- 代码变更后必须显式 `codemogger_index`；否则 `references`/`context` 全部是旧快照，
  且**没有任何警告**（只是结果变少/查不到）。
- `imports` 表随索引重建，旧 import 关系会在新索引里消失；实验期已遇到过「改了 schema 但旧库没更新
  → `no such column: body`」这类漂移。

## 3. 检索模式的真实语义（容易误解）

- MCP 的 `search` → CLI `search`，CLI 默认 **`--mode semantic`（limit=5）**，MCP 层未暴露 `mode`/`limit`。
  所以每 root 最多 5 条、且常出现「名字与查询词无关但语义相关」的结果，这是设计不是 bug。
- **keyword(FTS) 模式只能裸调 CLI**：`node /usr/local/lib/node_modules/codemogger/dist/cli.mjs search "<q>" --mode keyword --db <db>`。
- 补丁带来的 `body` 列（拆驼峰后入 FTS）**实测有效**：
  keyword `metadata` 命中 `recordTriggeredBy`（其 signature 里有 `setTaskMetadata`，
  整 token 无法被 keyword 匹配 ⇒ 只能来自 body 列的驼峰拆分）。
- keyword 仍不索引**.vue 的 `<template>` 正文**、`<style>`；只 Script 块。

## 4. `references` 三坑（shim 已缓解两坑）

| 坑 | 根因 | 缓解 |
|---|---|---|
| 符号名精确匹配 | `references <sym>` 精确匹配 `imports.name`，猜错名即空 | shim 启发式回退：无结果且 root 下有同名 `<sym>.{ts,tsx,vue}` 时自动改按 `--module "@/relpath"` 查（stderr 提示已回退） |
| `--file` 需绝对路径 | `imports.file_path` 存绝对路径，传相对路径静默零命中 | shim 自动转绝对 |
| 只解析静态 import | walker 只看静态 `import`/`export … from` | **未修**：动态 `import()`、字符串说明符不可见；动态引用请用 `grep` 复核 |

额外：库为空时的返回是 `No imports found for: X`，与「确实没人 import」同形，务必先 `list` 确认真有索引。

## 5. WAL 旁文件导致的「库看起来是空的」

实测：把一个正常的 13MB `index.db` 拷到 `/workspace/.codemogger/`，旁边残留着旧的
`index.db-wal` / `index.db-tshm`（早先空库留下的），libSQL 打开后 `related` 报
`no codebase indexed`；把两个旁文件移走后立刻读到 `489 files indexed (3909 chunks)`。

⇒ 排障顺序：`kv 文件本身存在且有数据` → `是否残留孤立的 -wal/-tshm` → `是否已 checkpoint`。

## 6. `related` 的行为要点

- 直接读 libSQL，不经 shim（所以 shim 的子命令表里没有 `related`）。
- token 策略刻意**不拆驼峰**（`taskService` 是整 token；`task`/`service` 太泛会淹没图），
  与 `body` 列（拆驼峰）策略相反——这是有意的：前者图精度，后者 recall。
- 默认 `depth=3 / maxNodes=200 / threshold=0.05`；`*>30 个文件*`共有的 token 被判为泛词丢弃（防洪水）。
- 输出含 `excludedInterference`：被判为文档/配置/测试的干扰文件（图里没有但 grep 会捞出来的东西）。
- seed 可以是文件路径（存在且是文件）→ 走 `seed:file`；否则按 token 走 symbol/module/define/hidden。

## 7. 覆盖不到的东西（不要指望它）

| 能力 | 状态 |
|---|---|
| `<template>` 里的逻辑（`@click` 处理函数名） | ❌ 不索引 |
| `<style>` / `.scss` 内容 | ❌（但 `css_source` 可从编译产物反查 SCSS 源） |
| 动态 `import()` / 字符串说明符 | ❌ 引用图看不到 |
| 子串 / 正则搜索 | ❌ FTS 是 token 级 BM25（用 `grep` 工具） |
| 类方法粒度 | 仅当类/对象 >150 行（`MAX_CHUNK_LINES`）才拆出方法级 chunk |
| 原生 `.rs`/`.swift`/`.dart` 等未配置扩展名 | ❌ 直接跳过文件 |
| 波及面的传递闭包（`impact` 只给一层 importer） | ❌ 用 `related` 多跳 |

## 8. 时间成本（实测）

| 操作 | 实测 |
|---|---|
| 单 root FTS 检索 | 135–190 ms/root |
| 6 root 全量索引 | 8–12 分钟（视磁盘/CPU） |
| `index` 经 MCP | 有超时上限；超大仓库建议分 root 索引或后台执行 |
| 概念查询（如 `SPA`） | 返回可达 ~250 条，建议 `format:"json"` + 二次过滤 |
