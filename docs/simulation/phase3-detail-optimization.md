# Phase 3 Spec — 细节补充 + 性能优化

> **阶段目标**：填充世界细节、全面性能优化、达到 Android <100MB 目标
> **状态**：v0.1 — 规划中
> **前置依赖**：Phase 1（后端核心）+ Phase 2（前后端联通）
> **后续阶段**：Phase 4（前端交互 + 前端性能）

---

## 一、阶段目标

本阶段是"量变到质变"的关键阶段：

1. ✅ **填充细节**：NPC 个性 / 组织生态 / 区域经济 / 事件系统 深度化
2. ✅ **性能优化**：内存从 ~140MB → <100MB，CPU 占用降低 30%+
3. ✅ **Android 适配**：针对移动端 CPU/GPU/内存特性做专项优化
4. ✅ **长稳验证**：30 分钟连续运行无内存泄漏、无性能退化

### 3.4 存储分层优化（对抗无限膨胀）

> **核心问题**：世界系统随运行时间无限膨胀——事件日志、关系变化、生命事件、脑系统数据...永不删除的话，Android 设备存储迟早撑爆。
> **核心思路**：参考云厂商对象存储分层（S3 Standard → IA → Glacier → Deep Archive），按数据温度分层，牺牲冷数据读写性能换取存储大幅减少。

#### 3.4.1 四层存储架构

```
┌─────────────────────────────────────────────────────┐
│  L0 热存储 (Hot) — 内存 + 热数据库表                 │
│  目标：读写最快，容纳当前活跃数据                      │
│  内容：焦点NPC / 活跃组织 / 当前事件 / 近期关系       │
│  容量：< 100 MB（内存）+ < 500 MB（磁盘）            │
│  保留期：游戏内 30 天 / 现实 7 天                    │
├─────────────────────────────────────────────────────┤
│  L1 温存储 (Warm) — 数据库 + 轻量压缩                │
│  目标：平衡性能与空间，容纳近期历史                    │
│  内容：非焦点NPC / 历史事件(近30天) / 旧关系快照      │
│  容量：< 2 GB                                        │
│  保留期：游戏内 1 年 / 现实 30 天                    │
├─────────────────────────────────────────────────────┤
│  L2 冷存储 (Cold) — 磁盘文件 + 高压缩                │
│  目标：空间最小，可接受秒级读取延迟                    │
│  内容：死亡NPC档案 / 历史事件归档 / 旧快照            │
│  格式：zstd 压缩的二进制分片（每游戏年一个分片）      │
│  容量：< 5 GB（游戏内 100 年估算）                   │
│  保留期：永久（但可手动清理旧时代）                   │
├─────────────────────────────────────────────────────┤
│  L3 极冷 (Frozen) — 统计代理，无原始数据             │
│  目标：完全不存个体，只存分布参数                      │
│  内容：远古时代NPC → 只存人口统计/分布函数/时代特征   │
│  容量：< 1 MB / 时代                                  │
│  保留期：永久                                         │
└─────────────────────────────────────────────────────┘
```

#### 3.4.2 核心优化策略

**策略 1：事件溯源 + 周期快照（Event Sourcing + Periodic Snapshot）**

不存每 tick 的完整状态，只存事件流 + 每 N tick 存一次快照：
```
状态(t) = 最近快照 + Σ(从快照到t的事件增量)
```

| 快照层级 | 间隔 | 保留数量 | 用途 |
|---------|------|---------|------|
| Tick 快照 | 100 tick | 10 个 | 近期回滚 / 增量同步 |
| 日快照 | 1 游戏日 | 30 个 | 日级查询 / 对比 |
| 月快照 | 1 游戏月 | 12 个 | 月级统计 / 时代划分 |
| 年快照 | 1 游戏年 | 永久（L2） | 年级历史 / 时代特征 |

**收益**：磁盘占用减少 90%+（事件比状态小得多 + 快照稀疏）。

---

**策略 2：死亡 NPC 数据降级（Death Downgrade）**

NPC 死亡后立即从 L0 热存储移除，按以下分级处理：

| 死亡时长 | 存储层级 | 保留内容 | 可查询性 |
|---------|---------|---------|---------|
| < 30 天 | L1 | 完整属性 + 死亡前 100 条事件 | 完整查询 |
| 30 天 ~ 1 年 | L2 压缩 | 核心属性 + 生命事件摘要 + 关系统计 | 需解压（秒级） |
| > 1 年 / 无名 NPC | L3 统计 | 只计入死亡人口统计 / 物种分布 | 不可查个体 |

**特殊保留**：玩家相关 NPC、著名 NPC（有过重大事件的）永久保留在 L2。

**收益**：死亡 NPC 占总人口的 90%+（长时间运行后），降级后热存储压力锐减。

---

**策略 3：关系网稀疏化 + 折叠（Graph Sparsification）**

关系是 O(N²) 级别的存储炸弹，必须做稀疏化：

| 关系类型 | 存储策略 | 折叠方式 |
|---------|---------|---------|
| 直系亲属（父母/子女/配偶） | 永久存 L1 | 不折叠 |
| 朋友 / 同事 | 只存活跃的 top-20 | 其余折叠为「认识 N 人」统计 |
| 弱关系（一面之缘） | 只存计数，不存个体 | 直接折叠为数字 |
| 组织成员关系 | 存成员 ID 列表 | 超过 1000 人 → 存分页 + 统计 |
| 敌对 / 竞争 | 只存活跃冲突 | 历史冲突折叠为事件摘要 |

**查询时的透明降级**：
- 问「张三的朋友有哪些」→ 返回 top-20 + 「还有 347 个普通朋友」
- 问「张三和李四认识吗」→ 弱关系也能查（从计数反向 bloom filter 验证）

**收益**：关系存储量减少 95%+，从 O(N²) 降到 O(N)。

---

**策略 4：事件日志分层压缩**

事件是最大的存储消耗源，分层处理：

| 事件年龄 | 存储层级 | 编码方式 | 压缩比 |
|---------|---------|---------|--------|
| < 1 游戏日 | L0 内存环形缓冲 | 原生 struct | 1x |
| 1 日 ~ 30 日 | L1 数据库 | delta 编码 + 列存 | 3~5x |
| 30 日 ~ 1 年 | L2 分片文件 | zstd 压缩二进制 | 10~20x |
| > 1 年 | L3 统计聚合 | 只存事件类型分布 / 频率 | 100x+ |

**事件 delta 编码**：同一 NPC 的连续事件，只存变化字段（比如生命事件只存类型+时间，不重复存 ID/名字等）。

**按时间分片**：每游戏月一个分片文件，旧分片整体压缩，永不修改（append-only）。

---

**策略 5：脑系统按需生成（Stateless Brain）**

脑系统是存储的另一大巨头——100 个焦点 NPC × 1000 格 = 10 万格，如果 1 万 NPC 都有脑就是 1 亿格。

**优化思路**：
- **焦点 NPC（~100 个）**：完整脑 + 格缓存，存在 L0
- **非焦点 NPC**：脑是**无状态**的——需要时从 NPC 属性 + 随机种子**临时生成**，用完丢弃
- **格记忆**：只存焦点格的长期记忆，其余格的状态完全由种子 + 当前 tick 决定
- **重要记忆锚点**：比如「初恋」「丧亲」等重大事件锚点存在 NPC 属性里，作为脑生成的固定参数

**本质**：脑不是存出来的，是算出来的。NPC 的性格/记忆/偏好都编码在其属性 + 生命事件里，脑系统只是把这些属性「表现」出来。

**收益**：非焦点 NPC 的脑存储 = 0，减少 99% 的脑系统存储。

---

**策略 6：统计代理模式（Statistical Proxy）**

这是整个架构对抗规模的根本策略——**绝大多数实体根本不存**。

| 实体规模 | 存储方式 | 占总存储比 |
|---------|---------|-----------|
| 焦点 NPC（~100） | 全量属性 + 完整脑 + 完整关系 | ~50% |
| 热 NPC（~10K） | 全量属性 + 缓存 | ~30% |
| 温 NPC（~100K） | 数据库存储，按需加载 | ~15% |
| 冷 NPC（~10M-1） | 不存个体，只存统计分布 | ~5% |

**统计代理的查询模式**：
- 「查询 ID=9999999 的 NPC」→ 用 ID 做种子，**实时生成**属性（确定性算法）
- 「全城有多少铁匠？」→ 从职业分布统计直接返回
- 「给我找一个精灵族法师」→ 从分布 + 种子生成一个符合条件的虚拟 NPC

**一致性保证**：同一个 ID 每次生成的结果完全一致（确定性算法 + 固定种子），用户察觉不到区别。

**收益**：10M NPC 实际只存 100K，存储减少 99%。

#### 3.4.3 数据迁移流水线

```
L0 热 ──(老化策略)──> L1 温 ──(月度归档)──> L2 冷 ──(年度聚合)──> L3 统计
        ↑                    ↑                    ↑
    加载回热              解压查询              统计反推
    （重新活跃）          （用户查询）          （只能看趋势）
```

**迁移触发**：
- 按时间自动迁移（每日 cron 检查老化数据）
- 按存储容量触发（超过阈值强制迁移最老数据）
- 手动触发（用户「清理旧数据」功能）

#### 3.4.4 存储预算与自动治理

| 层级 | 硬预算 | 超出时行为 |
|------|--------|-----------|
| L0 内存 | 100 MB | 淘汰最久未用的 NPC / 格 |
| L0 磁盘（热库） | 500 MB | 迁移最老数据到 L1 |
| L1 温库 | 2 GB | 迁移最老分片到 L2 |
| L2 冷存储 | 5 GB | 提示用户清理，或自动聚合最老时代到 L3 |
| L3 统计 | 无上限（可忽略） | — |

**自动治理任务**（每日运行）：
1. 检查各层存储用量
2. 迁移超时数据到下一层
3. 超过硬预算 → 强制淘汰 / 压缩
4. VACUUM 数据库回收空间
5. 生成存储用量报告

#### 3.4.5 预期效果

| 指标 | 优化前 | 优化后 | 缩减比 |
|------|--------|--------|--------|
| 10 年运行总存储 | ~50 GB（估算） | < 3 GB | ~94% |
| 热存储（活跃） | 随时间增长 | < 500 MB | 有界 |
| NPC 人均存储 | ~200 B（全存） | ~2 B（统计代理） | ~99% |
| 事件存储/游戏年 | ~1 GB | ~50 MB（L2压缩） | ~95% |
| 关系存储 | O(N²) 爆炸 | O(N) 可控 | ~99% |

### 5.2 长稳测试

长稳测试（Stability Test）是验证系统在持续运行下是否存在内存泄漏、性能退化、资源泄漏等问题的关键手段。

#### 5.2.1 测试分类

| 测试项 | 时长 | 指标阈值 | 触发方式 |
|--------|------|---------|---------|
| 内存泄漏检测 | 30 分钟 | HeapInuse 增长 < 5% | CI 定时 + 手动 |
| 性能退化检测 | 30 分钟 | tick 速率下降 < 10% | CI 定时 + 手动 |
| 数据库膨胀检测 | 30 分钟 | DB 文件增长 < 10% | CI 定时 + 手动 |
| Goroutine 泄漏检测 | 30 分钟 | goroutine 数波动 < 20% | CI 定时 + 手动 |
| 句柄泄漏检测 | 30 分钟 | 打开文件句柄稳定 | 手动 / 真机 |
| 长周期仿真 | 8 小时 | 世界生态不崩溃 | 手动 / 夜间 |

#### 5.2.2 测试方法

```bash
# 方式一：内置长稳测试（3 分钟，快速验证）
go test -run TestStability_3MinuteRun -timeout 5m ./internal/simverse/ -v

# 方式二：30 分钟完整长稳测试（CI 用）
ENCV_STABILITY_FULL=1 go test -run TestStability_Full30Min -timeout 45m ./internal/simverse/ -v

# 方式三：Go 内置 pprof 持续采样
go test -run TestStability_Full30Min -memprofile mem.prof -cpuprofile cpu.prof ./internal/simverse/
```

#### 5.2.3 观测指标

每 30 秒采样一次，记录以下指标：

| 指标类 | 具体指标 | 获取方式 |
|--------|---------|---------|
| 内存 | HeapInuse / HeapAlloc / HeapObjects | runtime.ReadMemStats |
| 内存 | GC 次数 / GC 停顿时间 | runtime.ReadMemStats |
| CPU | tick 耗时 / 每 tick 事件数 | 内部计时 |
| 协程 | goroutine 数量 | runtime.NumGoroutine |
| 缓存 | NPC 缓存命中率 / 大小 | cache.HitRate() / cache.Len() |
| 世界 | 存活 NPC 数 / 组织数 / 事件数 | world.Stats() |
| 数据库 | DB 文件大小 / 读写次数 | SQLite / ObjectBox stats |

#### 5.2.4 通过标准

1. **内存泄漏**：30 分钟内 HeapInuse 增长 < 5%（排除 GC 周期波动）
2. **性能退化**：前 5 分钟平均 tick 耗时 vs 最后 5 分钟，下降 < 10%
3. **Goroutine 泄漏**：稳定阶段 goroutine 数波动 < 20%
4. **数据一致性**：随机抽查 100 个 NPC，数据符合统计分布
5. **世界自洽**：人口/经济/组织数量不出现指数级爆炸或归零

#### 5.2.5 CI 工作流

独立工作流：`.github/workflows/simverse-stability.yml`

- **触发方式**：`schedule`（每日凌晨） + `workflow_dispatch`（手动） + `ci:stability` 标签
