# 模拟经营系统（SimVerse）— 技术规划 v0.1

> **项目代号**：SimVerse（Simulated Universe）
> **阶段**：规划验证期（只写验证代码和文档，不实现业务逻辑）
> **目标**：在移动设备上运行一个可容纳千万级 NPC、百万级组织的虚拟世界，持续产生随机事件

---

## 一、愿景与定位

### 1.1 核心愿景

在现有「特色微服务内核 + 多引擎数据库 + 任务系统」的架构之上，构建一个**轻量化模拟经营沙盒**：

- 不是游戏，是一个**可演化的虚拟世界引擎**
- 不是 3D 渲染，是**纯数据驱动的社会性模拟**
- 不是单机静态数据，是**持续演化的活生态**

### 1.2 规模目标

| 指标 | 目标值 | 说明 |
|------|--------|------|
| NPC 实体数 | **10,000,000**（千万级） | 有独立行为、属性、关系的个体 |
| 组织实体数 | **1,000,000**（百万级） | 家族、商会、帮派、村庄、城市等 |
| 平均内存占用 | **< 100 MB** | 安卓端运行约束 |
| 事件生成速率 | **1,000 ~ 10,000 事件/秒** | 持续不断的随机事件 |
| 世界模拟速率 | 1x ~ 100x 可调 | 游戏时间/真实时间比 |
| 验证测试时长 | 3 ~ 16 分钟 | 从冷启动到稳态验证 |

### 1.3 安卓端运行约束（铁律）

| 资源 | 约束值 | 检测方式 |
|------|--------|----------|
| 平均内存（PSS） | < 100 MB | `dumpsys meminfo` 10 分钟平均值 |
| 峰值内存（PSS） | < 150 MB | 同上述 |
| CPU 使用率（空闲模拟） | < 5%（8 核设备） | `top -m 5` 采样 |
| CPU 使用率（全速模拟） | < 40%（8 核设备） | 同上 |
| 电池消耗 | < 5%/小时（全速） | 实测 |
| 冷启动时间 | < 3 秒（千万级数据） | 从启动到可交互 |

> **关键假设**：千万级实体不可能全放在内存里。99% 的实体必须**常驻磁盘**，只在需要时加载到内存。这是整个系统的核心挑战。

### 2.2 核心模块划分

| 模块 | 职责 | 内存常驻量 | 磁盘 IO 模式 |
|------|------|-----------|-------------|
| **WorldClock** | 世界时间推进、tick 调度 | < 1 MB | 无 |
| **EventScheduler** | 事件队列、优先级调度、超时管理 | 5 ~ 20 MB | 批量写（事件日志） |
| **EntityManager** | 实体缓存、LRU 换入换出、引用计数 | 20 ~ 50 MB | 高频随机读写 |
| **BehaviorEngine** | NPC AI、组织演化、关系计算 | 10 ~ 30 MB | 批量读（行为需要的数据） |
| **RelationGraph** | 实体间关系（社交、组织、敌对） | 10 ~ 20 MB | 批量读写 |
| **EconomySim** | 经济系统、物价、供需、贸易 | 5 ~ 10 MB | 低频批量 |
| **EventLogger** | 事件持久化、历史回溯 | < 5 MB | 顺序追加写 |

> 总内存预算：100 MB - 20 MB（Go runtime + 微内核 + 任务系统） = **80 MB 可用**

### 2.3 与现有系统的关系

- **特色微内核（MicroKernel）**：SimVerse 作为一组服务注册到微内核中，享受服务级生命周期管理、内存守卫、租户隔离
- **任务系统（TaskSystem）**：长时间模拟任务（如"模拟 100 年"）通过任务系统调度，支持暂停/继续/进度
- **多引擎数据库**：不同类型的数据用不同的引擎存储（详见 §三）

## 三、数据存储策略（核心！）

### 3.1 数据库引擎选型矩阵

| 数据类型 | 数量级 | 访问模式 | 推荐引擎 | 原因 |
|----------|--------|----------|----------|------|
| NPC 基础属性 | 10M | 随机读写、按 ID 查 | **ObjectBox** | 高性能对象存储，按 ID 查找 O(1) |
| 组织实体 | 1M | 随机读写、按类型查 | **ObjectBox** | 同上，类型安全查询 |
| 关系数据 | 50M+ | 图遍历、邻接查询 | **SQLite/LibSQL** | 关系型 + 向量索引（未来） |
| 事件日志 | 无限增长 | 追加写、范围读 | **SQLite** | WAL 模式顺序写快 |
| 经济数据 | 100K | 聚合查询、统计 | **SQLite/LibSQL** | SQL 聚合能力强 |
| 热数据缓存 | 10K ~ 100K | 全内存访问 | Go map + LRU | 内存中，不需要持久化 |

### 3.2 实体分级存储策略

**关键洞察**：千万级 NPC，99% 是"沉睡"的——它们不活跃、不被关注、不需要每 tick 都计算。

```
Tier 0: 内存热数据（~10,000 实体）
  └── 当前活跃的 NPC、玩家关注的实体、正在事件中的实体
  └── LRU 缓存，最近最少使用的换出到磁盘
  └── 占内存：~10 MB（每个实体 ~1 KB）

Tier 1: 温数据（~1,000,000 实体）
  └── 有组织归属、有社会关系的 NPC
  └── 按组织/区域批量加载，批量计算后写回
  └── 占内存：~100 MB（批量加载时瞬时）
  └── 常驻磁盘，按需换入

Tier 2: 冷数据（~9,000,000 实体）
  └── 无组织、无关系、沉睡的 NPC
  └── 只在被事件触发时才激活
  └── 绝大部分时间躺在磁盘上
  └── 占内存：0 MB（纯磁盘）
```

### 3.3 内存预算明细

| 用途 | 预算 | 说明 |
|------|------|------|
| Go Runtime | ~15 MB | 堆 + 栈 + GC |
| 微内核 + 任务系统 | ~5 MB | 服务注册 + 任务队列 |
| 热实体缓存（Tier 0） | ~20 MB | 20,000 实体 × 1 KB |
| 批量计算缓冲区 | ~20 MB | Tier 1 批处理 |
| 事件队列 | ~10 MB | 待处理事件 |
| 关系图缓存 | ~10 MB | 热点关系子图 |
| 数据库连接/缓存 | ~10 MB | 连接池 + 页缓存 |
| **合计** | **~90 MB** | 留 10 MB 余量 |

## 四、NPC 实体设计

### 4.1 实体数据结构（最小化）

> 目标：每个 NPC 实体序列化后 < 512 字节。10M × 512B = 5 GB 磁盘空间（可接受）。

```go
type NPC struct {
    ID          uint64    // 8 字节 — 全局唯一 ID
    Name        string    // ~20 字节 — 名字（压缩存储）
    Age         uint16    // 2 字节 — 年龄
    Health      uint16    // 2 字节 — 生命值 0-1000
    Energy      uint16    // 2 字节 — 精力值 0-1000
    
    // 属性（bit-packing，每个属性 6 位 = 0-63）
    Strength    uint8     // 力量
    Intelligence uint8    // 智力
    Charisma    uint8     // 魅力
    Agility     uint8     // 敏捷
    Luck        uint8     // 幸运
    
    // 状态（bitmask）
    Status      uint16    // 存活/生病/受伤/忙碌/...
    
    // 归属
    OrgID       uint32    // 所属组织 ID（4 字节）
    RegionID    uint32    // 所在区域 ID（4 字节）
    
    // 时间戳
    LastActive  int64     // 8 字节 — 最后活跃时间（游戏时间）
    BornAt      int32     // 4 字节 — 出生时间（游戏时间，day）
    
    // 预留
    Reserved    [32]byte  // 32 字节 — 未来扩展
}
```

**估算**：8 + 20 + 2×4 + 5 + 2 + 4 + 4 + 8 + 4 + 32 = **~95 字节 + 字符串开销**
实际序列化后估计 200 ~ 300 字节。10M × 300B = **3 GB 磁盘**（可接受）。

### 4.2 实体激活模型

| 激活级别 | 触发条件 | 计算频率 | 占比 |
|----------|----------|----------|------|
| **Active** | 玩家关注 / 正在事件中 / 组织领袖 | 每 tick | ~0.1% (10,000) |
| **Warm** | 属于活跃组织 / 有活跃关系 | 每 N tick (N=10~100) | ~10% (1M) |
| **Cold** | 普通个体，无特殊事件 | 每天一次（游戏时间） | ~90% (9M) |
| **Dormant** | 长期无活动，进入"冬眠" | 触发才唤醒 | 动态调整 |

**休眠机制**：连续 N 天无事件的 NPC 进入 Dormant 状态，压缩存储（只保留 ID + 基础属性），需要时重新"解冻"。

## 五、事件系统设计

### 5.1 事件分类

| 事件类型 | 频率 | 影响范围 | 示例 |
|----------|------|----------|------|
| **个人事件** | 高（~10K/s） | 单实体 | 生病、工作、休息、购物、学习 |
| **交互事件** | 中（~1K/s） | 2~10 实体 | 交易、对话、冲突、合作 |
| **组织事件** | 低（~100/s） | 组织内 | 集会、战争、选举、贸易 |
| **区域事件** | 极低（~10/s） | 区域内 | 灾难、节日、市场波动 |
| **世界事件** | 极低频（~1/min） | 全局 | 季节变化、大灾难、科技突破 |

### 5.2 事件调度算法

```
时间轮（Timing Wheel）+ 优先级队列
  ├── 短时间轮（秒级）：即将发生的事件
  ├── 中时间轮（分钟级）：近期事件
  └── 长时间轮（小时/天级）：远期事件

事件生成：
  1. 每个 tick，从时间轮取出到期事件
  2. 根据实体状态和环境，概率性生成新事件
  3. 新事件根据预计发生时间放入对应时间轮
  4. 事件优先级决定执行顺序
```

### 5.3 事件日志

- 所有事件持久化到 SQLite（WAL 模式，顺序写入）
- 支持时间回溯（"3 天前发生了什么？"）
- 事件日志可以压缩归档（冷数据）

## 六、组织系统设计

### 6.1 组织类型

| 层级 | 类型 | 典型规模 | 数量级 |
|------|------|----------|--------|
| L1 | 家庭 / 小队 | 2 ~ 10 人 | ~2M |
| L2 | 村庄 / 商会分会 | 50 ~ 500 人 | ~100K |
| L3 | 城市 / 大家族 | 1K ~ 10K 人 | ~10K |
| L4 | 王国 / 大商会 | 100K ~ 1M 人 | ~100 |
| L5 | 联盟 / 帝国 | 1M+ 人 | < 10 |

### 6.2 组织演化

- **自组织**：NPC 会自发组建家庭、加入商会、建立帮派
- **层级晋升**：能力强的 NPC 会在组织中晋升
- **分裂与合并**：组织可以分裂（内乱）或合并（联姻/吞并）
- **兴衰周期**：组织有生命周期——创立、发展、鼎盛、衰落、灭亡

### 6.3 组织计算优化

- **按组织批处理**：同一个组织的 NPC 一起计算，减少随机 IO
- **组织属性聚合**：组织的整体属性 = 成员属性的聚合（不需要逐个算）
- **事件冒泡**：低层事件如果影响足够大，会冒泡到高层组织级

## 七、性能与优化策略

### 7.1 核心优化方向

| 优化手段 | 预期收益 | 实现难度 |
|----------|----------|----------|
| **实体分级 + LRU 缓存** | 内存占用减 90%+ | 中 |
| **按组织/区域批处理** | 磁盘 IO 减 90%+ | 高 |
| **ObjectBox 按 ID 直读** | 随机读延迟 < 1μs | 低（已有引擎） |
| **事件时间轮** | 调度效率 O(1) | 中 |
| **数据压缩（冷数据）** | 磁盘占用减 50%+ | 中 |
| **SIMD / 批量计算** | 计算速度提 2~10 倍 | 高 |
| **增量计算** | 只计算变化的部分 | 高 |

### 7.2 数据库引擎分工

- **ObjectBox**：实体存储（按 ID 超快访问、类型安全查询、批量写入）
- **SQLite / LibSQL**：关系数据、事件日志、聚合统计
- **LibSQL 向量索引**（未来）：NPC 相似度匹配、推荐

## 十、风险与挑战

### 10.1 技术风险

| 风险 | 概率 | 影响 | 缓解方案 |
|------|------|------|----------|
| 内存超标 | 高 | 致命 | 严格的分级存储 + LRU + 压缩 |
| 磁盘 IO 瓶颈 | 中 | 严重 | 批量读写 + 分级存储 + ObjectBox 优化 |
| 事件爆炸（正反馈） | 中 | 严重 | 事件限流 + 优先级丢弃 + 流量控制 |
| 数据一致性 | 低 | 严重 | 事务 + 校验 + 幂等设计 |
| GC 停顿过长 | 中 | 体验差 | 对象池 + 减少分配 + 值类型 |

### 10.2 可行性自问

> ❓ 千万级实体 + < 100MB 内存，是不是天方夜谭？

**不是。** 关键在于：
1. **99% 的实体在磁盘上**（冷数据），内存只放热数据
2. **每个实体很小**（~300 字节），100M 内存可以放 30 万+实体
3. **计算也是分级的**——冷实体每天只算一次，不是每 tick
4. **ObjectBox 按 ID 读取极快**（mmap，近似内存访问速度）

实际在游戏行业，类似技术已被验证可行（如 EVE Online 的"时间膨胀"、各类 MUD 的分区/休眠机制）。

## 十三、ComboLite 插件化架构

### 13.1 为什么插件化

SimVerse 作为 ComboLite 插件的好处：

| 维度 | 独立应用 | ComboLite 插件 |
|------|---------|---------------|
| **安装方式** | 单独安装 APK | 主应用内插件市场一键安装 |
| **更新方式** | 应用商店更新 | 插件热更新，不重启主应用 |
| **资源共享** | 各自打包 | 复用主应用的后端服务、数据库、组件库 |
| **包体积** | 完整 APK (~30MB+) | 插件 APK (~0.5MB) + 前端资源 |
| **生命周期** | 独立进程 | 主应用进程内，共享 ClassLoader |

### 13.3 关键设计决策

#### 13.3.1 虚拟 HTTPS 域名（替代 file:// 协议）

**问题**：file:// 协议加载 HTML 会触发 CORS 限制，Origin 为 null，无法加载 CSS/JS 子资源。

**方案**：使用虚拟 HTTPS 域名 `https://simverse-plugin.local/`，通过 `shouldInterceptRequest` 拦截请求，从 assets 目录读取资源。

```kotlin
override fun shouldInterceptRequest(view: WebView, request: WebResourceRequest): WebResourceResponse? {
    val url = request.url.toString()
    if (url.startsWith(VIRTUAL_BASE_URL)) {
        val path = url.removePrefix(VIRTUAL_BASE_URL).removePrefix("/")
        val assetPath = "simverse/${if (path.isEmpty()) "index.html" else path}"
        // 从 assets 读取，设置正确的 MIME type
        return createWebResourceResponse(assetPath)
    }
    return super.shouldInterceptRequest(view, request)
}
```

**好处**：
- ✅ 正常的 Origin（`https://simverse-plugin.local`）
- ✅ 支持相对路径资源加载
- ✅ 后端 CORS 可精确控制允许的域名

#### 13.3.2 JSInterface 双模式适配

**问题**：前端开发时在浏览器中运行，没有原生 JSInterface；在插件 WebView 中运行时，需要调用原生方法。

**方案**：SimVerse.ts 插件封装层提供双模式：

```typescript
// 检测是否运行在原生插件模式
const nativeBridge = (window as any).SimVerseNative as SimVersePlugin | null;

// 网页开发模式的 fallback 实现
const webImpl: SimVersePlugin = {
  async openWorld(_options) { console.warn("[SimVerse] not available in web mode"); },
  async closeWorld() { /* ... */ },
  // ...
};

// 调用时优先使用原生，fallback 到 web 实现
function callNative<K extends keyof SimVersePlugin>(method: K, ...args) {
  if (nativeBridge && typeof (nativeBridge as any)[method] === "function") {
    return (nativeBridge as any)[method](...args);
  }
  return (webImpl[method] as any)(...args);
}
```

**已替换的 Capacitor 插件**：

| 功能 | Capacitor 插件 | JSInterface 方法 |
|------|--------------|-----------------|
| 屏幕方向锁定 | `@capacitor/screen-orientation` | `lockOrientation()` / `unlockOrientation()` |
| 打开/关闭世界 | （自定义） | `openWorld()` / `closeWorld()` |
| 心跳服务 | （自定义） | `startHeartbeat()` / `stopHeartbeat()` |
| 添加桌面快捷方式 | （自定义） | `addShortcut()` / `isShortcutSupported()` |
| 诊断面板 | （自定义） | `showDiagnostic()` |

#### 13.3.3 前端构建与插件打包分离

**原则**：Gradle 不负责前端构建，前端构建由 CI 或开发者手动执行。

**原因**：
1. Gradle 执行 npm/pnpm 需要 Node.js 环境，构建机可能没有
2. 前端构建是独立的工程，不应与 Android 构建耦合
3. 调试时可以单独改前端，不用重新编译 Kotlin

**工作流**：

```bash
# 1. 前端开发（热更新）
cd plugin-simverse/web
pnpm dev

# 2. 前端构建（产出 dist/）
pnpm build

# 3. 拷贝到 assets 目录（CI 或手动）
cp -r dist/* ../src/main/assets/simverse/

# 4. 构建插件 APK
cd ../..
./gradlew :plugin-simverse:assembleRelease
```

### 13.4 横屏世界视图的特殊处理

世界视图是横屏的，需要特殊处理：

1. **进入时锁定横屏**：`onMounted` 时调用 `lockScreenOrientation("landscape-primary")`
2. **退出时恢复竖屏**：`onUnmounted` 时调用 `unlockScreenOrientation()`
3. **底部菜单加退出按钮**：调用 `closeWorld()` 关闭 Activity
4. **双模式兼容**：网页开发模式下用 `window.history.back()` 替代
