## 三、实体大小与性能

### 3.1 NPC V2 实体结构

```
┌─────────────────────────────────────────┐
│  Header: 12 bytes                       │
│    ID (8B) + Species (1B) + Profession (2B) + Level (1B) │
├─────────────────────────────────────────┤
│  Vital Stats: 14 bytes                  │
│    Age (2B) + Health/MaxHealth (4B)     │
│    Energy/MaxEnergy (4B)                │
│    Mana/MaxMana (4B)                    │
├─────────────────────────────────────────┤
│  Mental Stats: 2 bytes                  │
│    Mood (1B) + Satisfaction (1B)        │
├─────────────────────────────────────────┤
│  Skills: 10 bytes (10 × 1B)             │
│    Str/Agi/Int/Cha/Per/End/Mag/Ste/Cra/Tra│
├─────────────────────────────────────────┤
│  Inventory: 40 bytes (10 × 4B)          │
├─────────────────────────────────────────┤
│  Bank: 40 bytes (10 × 4B)               │
├─────────────────────────────────────────┤
│  Affiliations: 12 bytes                 │
│    OrgID (4B) + RegionID (4B)           │
│    HomeRegionID (4B)                    │
├─────────────────────────────────────────┤
│  Timestamps: 8 bytes                    │
│    LastActive (4B) + BornAt (4B)        │
├─────────────────────────────────────────┤
│  Progression: 6 bytes                   │
│    Experience (4B) + WealthTier (1B)    │
│    + SocialTier (1B)                    │
├─────────────────────────────────────────┤
│  Faction Rep: 16 bytes (8 × 2B)         │
├─────────────────────────────────────────┤
│  Name: variable (1B len + up to 48B)    │
└─────────────────────────────────────────┘
```

**总计**：约 168 字节（含 10 字符名字）

## 四、内存模型分析

### 4.1 NPC 实体内存

| 规模 | 内存占用 | 说明 |
|------|----------|------|
| 10K NPC | ~2-3 MB | 结构体 + 字符串 + skills/resources 数组 |
| 100K NPC | ~20-30 MB | - |
| 1M NPC | ~200-300 MB | ⚠️ 已超 100MB 预算 |
| 10M NPC (全内存) | ~2-3 GB | ❌ 不可行 |

### 4.2 分级存储方案

**目标：10M NPC，总内存 < 100 MB**

| 层级 | 比例 | 数量 | 内存 | 存储介质 |
|------|------|------|------|---------|
| Tier 0 - 活跃 | 0.1% | 10,000 | ~3 MB | 内存（LRU Cache） |
| Tier 1 - 温数据 | 1% | 100,000 | ~25 MB | 内存（批量加载/卸载） |
| Tier 2 - 冷数据 | 98.9% | 9,890,000 | 0 MB | ObjectBox（磁盘） |
| **合计** | 100% | 10,000,000 | **~28 MB** | - |

加上其他系统开销：

| 系统 | 内存 |
|------|------|
| 热 NPC（10K） + 温 NPC（100K） | ~28 MB |
| 关系图（活跃 NPC 的关系，~20 边/人） | ~5 MB |
| 事件调度器（队列 ~10K 事件） | ~1 MB |
| 组织实体（1M，仅基础索引） | ~20 MB |
| 数据库引擎缓存（ObjectBox + SQLite） | ~15 MB |
| Go runtime + 微内核 | ~15 MB |
| 其他（地区、资源、缓冲） | ~10 MB |
| **总计** | **~94 MB** |

**结论：✅ 100 MB 预算可行**（留约 6 MB 余量）

### 4.3 关系图内存

| 场景 | 节点数 | 边数 | 内存 | 每边均摊 |
|------|--------|------|------|---------|
| 1K NPC × 20 边 | 1,000 | ~20K | ~1.9 MB | ~100 B |
| 10K NPC × 20 边 | 10,000 | ~200K | ~20 MB | ~100 B |
| 100K NPC × 20 边 | 100,000 | ~2M | ~200 MB | ~100 B |

**策略**：
- 只有 Tier 0 + Tier 1 的 NPC 关系在内存中
- Tier 2 冷数据的关系存储在 ObjectBox 的关系表中
- 需要时按需加载特定 NPC 的关系网

## 五、指数级交互与优化

### 5.1 问题：O(N²) 交互爆炸

如果每个 NPC 都和其他所有 NPC 交互：

| NPC 数量 | 可能的交互对 | 完全计算耗时（估算） |
|----------|-------------|---------------------|
| 100 | 4,950 | < 1ms |
| 1,000 | 499,500 | ~7ms |
| 10,000 | ~5000万 | ~750ms |
| 100,000 | ~50亿 | ~75秒 |
| 1,000,000 | ~5000亿 | ~2小时 |
| 10,000,000 | ~50万亿 | ~9天 |

**全量 O(N²) 完全不可行**。

### 5.2 五层优化策略

```
Layer 5: Lazy Evaluation (懒加载)
  └─ 只计算玩家能观察到的区域/实体
  
Layer 4: Event-Driven (事件驱动)
  └─ 只有 0.1%-1% 的 NPC 在任何 tick 中活跃
     （睡眠/工作/休息的 NPC 不触发交互）
  
Layer 3: Sparse Social Graph (稀疏社交图)
  └─ 每个 NPC 只有 ~10-50 个关系
     （家人、朋友、同事、敌人，不是所有人）
  
Layer 2: Spatial Partitioning (空间分区)
  └─ 只有同区域的 NPC 才能交互
     （按 Region/SubRegion 划分，O(N) 不是 O(N²)）
  
Layer 1: Batch Processing (批量处理)
  └─ 同职业/同组织的 NPC 批量计算
     （利用数据局部性，向量化计算）
```

### 5.3 优化后效果

**每 tick 实际交互数**：

| 指标 | 计算 | 数值 |
|------|------|------|
| 总 NPC | 10M | 10,000,000 |
| 活跃比例 | 1% | 100,000 |
| 空间分区大小 | 每个 region ~1000 人 | 1000 |
| 每人交互数 | 平均 5 次/tick | 5 |
| **每 tick 总交互** | 100K × 5 | **500,000** |
| 每次交互耗时 | 15 ns | - |
| **总计算时间** | 500K × 15ns | **7.5 ms** |

**结论：✅ 每 tick 仅需 ~7.5ms，完全可接受**（60fps 的 1 帧预算是 16ms）

## 六、数据库引擎横向对比

### 6.1 测试场景说明

使用任务系统 TaskData 作为基准实体（大小与 NPC V2 相当，~200-300 字节），测试三个引擎的 CRUD 性能。

**测试环境**：Linux amd64, Intel Xeon Platinum 8582C, Go 1.25.x

### 6.2 写入性能对比

| 操作 | SQLite (pure Go) | ObjectBox (CGO) | 对比 |
|------|-----------------|-----------------|------|
| 单条写入 | 614 μs/op | ~1.1 ms/op* | SQLite 略快 |
| 100条批量写入 | 68.8 μs/条 | 4.3 μs/条** | **ObjectBox 快 16 倍** |
| 1000条批量写入 | 27.4 μs/条 | 4.3 μs/条 | **ObjectBox 快 6 倍** |

> *ObjectBox 单条写入 benchmark 方式不同，仅供参考
> **基于 ObjectBox 官方 PutMany 性能

### 6.3 读取性能对比

| 操作 | SQLite (pure Go) | ObjectBox (CGO) | 对比 |
|------|-----------------|-----------------|------|
| 按 ID 单条读取 | 71 μs/op | ~190 μs/op* | SQLite 快 2.7 倍 |
| 列表 100 条 | 930 μs | - | - |

> *ObjectBox 读取需要类型转换，实际直接 Get ID 应该更快

### 6.4 场景适配分析

| 场景 | 推荐引擎 | 原因 |
|------|---------|------|
| 实体按 ID 随机读写 | ObjectBox | 批量写入快，mmap 读取 |
| 关系查询、过滤查询 | SQLite / LibSQL | SQL 的 JOIN / WHERE 更灵活 |
| 事件日志、时间序列 | SQLite / LibSQL | 索引 + 范围查询 |
| 向量搜索 | LibSQL | 内置向量索引 |
| 冷数据大容量存储 | ObjectBox | 高压缩、低内存占用 |

### 6.5 SimVerse 推荐架构：双引擎混合

```
┌─────────────────────────────────────────────────┐
│               Entity Manager                    │
├───────────────────┬─────────────────────────────┤
│  ObjectBox        │  SQLite / LibSQL            │
│  (实体存储)       │  (关系/事件/索引)            │
├───────────────────┼─────────────────────────────┤
│ • NPC 实体        │ • 关系表 (npc_relations)    │
│ • 组织实体        │ • 事件日志 (event_log)       │
│ • 区域实体        │ • 组织成员关系              │
│ • 资源库存        │ • 交易记录                  │
│                   │ • 技能/成就索引             │
└───────────────────┴─────────────────────────────┘
```

**内存分工**：
- ObjectBox：~10 MB（mmap 缓存）
- SQLite：~5 MB（WAL + 页缓存）
- 合计：~15 MB

| LibSQL 向量搜索性能 | 中 | Phase 1 实现后验证 |

| 风险 | 概率 | 影响 | 缓解方案 |
|------|------|------|----------|
| Android 端 GC 压力大 | 中 | 体验差 | 对象池 + 值类型 + 减少分配 |

### 9.4 Catch-up Simulation 核心机制

> **这是 v0.3 最重要的突破**——解决了"不观测就永不更新"的致命问题。

#### 核心思想

```
传统游戏:  每帧 tick 所有活跃 NPC → 10M NPC = 每帧卡死
我们的方案: NPC 休眠时不更新 → 被访问时一次性补算缺失时间
```

#### 补算算法

当访问一个 NPC 时：
1. 计算 `ticksPassed = currentTick - lastUpdateTick`
2. 根据生命阶段确定更新间隔 `interval`
3. 计算需要补多少次：`updates = ticksPassed / interval`
4. 对每次更新应用：
   - 年龄增长
   - 技能增长/衰退
   - 财富变化
   - 随机生活事件（小概率）
   - 生命阶段跃迁检查
5. 最后更新 `lastUpdateTick = currentTick`

#### 性能实测

| 指标 | 实测值 |
|------|--------|
| 10K NPC × 100K ticks 补算 | 1.1 ms |
| 每 NPC 每 tick | ~0.001 ns（极小） |
| 10M NPC 单日(1000 ticks)补算 | **~0.01 秒** |
| 10M NPC 一年(365K ticks)补算 | ~3.7 秒 |

**结论**：Catch-up 的成本极低，因为：
- 计算非常简单（纯算术 + 少量随机数）
- 没有 I/O（纯内存操作）
- 只在访问时才计算（懒加载）
- 冷数据根本不计算（用统计分布描述）

#### 全生命周期验证

单个 NPC 从出生到死亡的完整模拟：

```
婴儿期 → 童年 → 青少年 → 青年 → 中年 → 老年 → 百岁 → 死亡
  ↓        ↓       ↓        ↓       ↓       ↓       ↓
 成长    上学    择业/初恋  工作/结婚 事业巅峰  退休    高寿
                              ↓
                           生子/创业
```

- 平均一生经历 ~60-80 个生活事件
- 职业可能变化 1-3 次
- 可能有 0-5 个孩子
- 死亡年龄分布符合物种寿命曲线

### 9.5 关系网动态演化

#### 设计原则

- **不维护全量关系图**（10M NPC × 20 关系 = 2 亿条边，太大）
- **事件驱动 + 时间戳补偿**：
  - 热 NPC（在缓存中）的关系实时更新
  - 冷 NPC 的关系变化以事件形式存储（结婚、生子、交友、结仇）
  - 查询冷 NPC 关系时，根据最后访问时间 + 事件日志补算

#### 关系类型（12 种）

| 类别 | 关系 | 衰减速率 |
|------|------|---------|
| 家庭 | 父母 / 子女 / 兄弟姐妹 / 配偶 | 几乎不衰减 |
| 社交 | 朋友 / 恋人 / 恩师 / 仇敌 | 中等衰减 |
| 职业 | 同事 / 上司 / 下属 / 客户 | 较快衰减 |

#### 关系衰减公式

```
亲密度变化 = 基础值 × 时间因子 × 性格因子 × 互动频率
```

- 朋友关系：不互动每年衰减 ~10%
- 家庭关系：几乎不衰减（血缘绑定）
- 敌对关系：缓慢衰减（仇恨消散慢）

### 9.6 统计分布代理（冷数据优化）

> **这是另一个核心创新**——99% 的 NPC 根本不需要个体数据，用统计分布就能描述。

#### 三层架构

```
┌─────────────────────────────────────────┐
│  L1: 热数据 (10K NPC)                   │
│  全量个体数据 + 实时更新 + LRU 缓存      │  ~30 MB
├─────────────────────────────────────────┤
│  L2: 温数据 (1M NPC)                    │
│  压缩存储 + 按需加载 + Catch-up 补算     │  ~100 MB (在磁盘)
├─────────────────────────────────────────┤
│  L3: 冷数据 (9M+ NPC)                   │
│  区域统计分布 + 按需生成 + 统计采样      │  ~100 KB ✨
└─────────────────────────────────────────┘
```

#### 区域统计分布（每个 Region 维护）

| 统计项 | 用途 |
|--------|------|
| 人口总数 | 知道这个区域有多少人 |
| 年龄分布直方图 | 采样年龄时用 |
| 性别比例 | 采样性别时用 |
| 职业分布 | 采样职业时用 |
| 财富分布 | 采样财富时用 |
| 出生率 / 死亡率 | 人口动态平衡 |
| 资源产出/消耗速率 | 区域经济模拟 |
| 组织数量 / 规模分布 | 组织系统统计代理 |

#### 按需激活流程

当需要访问一个冷 NPC 时：
1. 从区域统计分布中采样初始属性
2. 根据 NPC ID 作为随机种子，确保每次生成一致
3. 用 Catch-up 补算到当前时间
4. 写入 LRU 缓存
5. 后续访问直接从缓存取

**关键性质**：同一个 NPC ID，每次从冷数据激活时，属性都是一致的（确定性种子）。这意味着——虽然 NPC 大部分时间"不存在"，但只要你去找它，它就一直在那里，而且它的人生轨迹是完整的。

### 9.7 内存开销对比

| 方案 | 10M NPC 内存 | 可行性 |
|------|-------------|--------|
| 全部个体数据在内存 | ~2-3 GB | ❌ 不行 |
| 全部个体数据在磁盘 + 10K 缓存 | ~30 MB（内存） | ✅ 可以，但磁盘 I/O 高 |
| **统计分布代理 + 按需激活** | **~30 MB（内存）** | ✅✅ **最优** |

**核心洞察**：大部分 NPC 你永远不会去访问它们。它们的存在只需要通过统计数据来体现——区域人口、经济指标、社会结构。只有当你真正去看某个人时，它才需要"实体化"。

这就像现实世界——你知道一个城市有几百万人，但你真正认识的只有几百个。其他人只是作为"人群"存在，但如果你随机拦住一个人，他会有自己完整的人生故事。

## 十、分形嵌套世界架构（v0.4 新增）

> **核心洞察**：世界本身是分形自相似的——世界由 NPC 组成，NPC 由"格"（神经元组）组成，格又由神经元组成……每一层都有相同的架构模式：实体 + 组织 + 关系网 + 生命周期 + 事件系统。

### 10.1 三层分形架构

```
L0 世界层
├── 实体: NPC (10M 统计, 10K 热)
├── 组织: 国家/公司/家族 (1M 统计, 10K 热)
├── 关系: 朋友/家人/同事 (200M 边统计, 200K 热)
├── 事件: 生活事件/社会事件
└── 存储: 统计分布代理 + LRU 缓存 + Catch-up

L1 NPC 层（脑内世界）
├── 实体: 格/神经元组 (每 NPC 860 亿统计, 1K 核心)
├── 组织: 脑区/神经核团 (8 个脑区)
├── 关系: 突触连接 (1000 万亿统计)
├── 事件: 放电/可塑性/形成-消退
└── 存储: 统计分布代理 + 按需采样 + 核心格缓存

L2 格层（神经元级）
└── (不模拟，太细了，用统计分布描述即可)
```

**分形自相似性**：
- 相同的架构模式（统计代理 + 缓存 + Catch-up）
- 相同的数据结构（实体 + 组织 + 关系 + 事件）
- 相同的性能优化策略
- 不同层级只调参数（规模、精度、更新频率）

### 10.2 玩家焦点辐射模型

玩家的关注范围像涟漪一样向外扩散，离玩家越近，模拟精度越高：

| 焦点层级 | NPC 数量 | 模拟精度 | 核心格数/NPC | 总核心格数 |
|---------|---------|---------|-------------|-----------|
| Player (L4) | 1 | 全精度实时 | 2000 | 2,000 |
| Core (L3) | ~100 | 高精度 | 1000 | 100,000 |
| Near (L2) | ~1,000 | 中精度 | 500 | 500,000 |
| Distant (L1) | ~10,000 | 低精度 | 100 | 1,000,000 |
| None (L0) | ~999 万 | 统计代理 | 0 | 0 |
| **总计** | **~1000 万** | — | — | **~160 万** |

> 实际核心格总数约 160 万，不是 1000 万 × 1000 = 100 亿。只有和玩家有关的 NPC 才需要核心格模拟，其他 NPC 用统计分布描述。

### 10.3 三层阶梯性能调度

根据系统资源状态，自动调整模拟强度：

| 层级 | 触发条件 | 事件速率 | 缓存大小 | 子模拟深度 |
|------|---------|---------|---------|-----------|
| **前台 60%** | 用户活跃使用 | 0.6x | 10K NPC | L2 深度 |
| **闲时 100%** | 后台 + 资源充足 | 1.0x | 20K NPC | L1 深度 |
| **深闲 300%** | 充电/深夜/长时间静置 | 3.0x | 50K NPC | L3 深度 |

**调度策略**：
- 前台模式：优先保证 UI 流畅，降低世界推演速率
- 闲时模式：正常后台推进，平衡性能与功耗
- 深闲模式：全速推演世界，批量 catch-up，补算大量冷数据

4. 玩家焦点收缩: 前台模式只保留核心圈 NPC

#### CPU 性能

| 操作 | 实测值 | 10M 规模预估 |
|------|--------|-------------|
| 1K NPC × 1000 ticks | 149 ms | ~1.5 s/天 (10K NPC) |
| NPC Catch-up 单 tick | ~0.1 ns | — |
| 格 Catch-up (待实现) | 预估 ~0.01 ns | — |
| 每日世界推进 | — | <5 秒 (后台批量) |

### 10.6 为什么这是可行的

1. **分形复用**：同一套引擎代码服务所有层级，研发成本低
2. **统计代理**：99.99% 的实体不需要个体数据，用分布描述即可
3. **按需激活**：只有被观察到的实体才"实体化"，其他都是统计数字
4. **Catch-up**：休眠的实体不更新，被访问时一次性补算（成本极低）
5. **焦点辐射**：离玩家越远精度越低，大部分资源集中在玩家关注的小范围
6. **三层调度**：根据系统状态动态调整，前台流畅、后台补全

### 10.7 可扩展性

这套架构可以**无限向下扩展**层级：
- L3: 神经元内的分子世界（离子通道、受体、神经递质）
- L4: 分子内的原子世界（量子态、化学键）
- L5: ……

每一层都复用相同的模式：统计分布代理 + 按需激活 + Catch-up Simulation + LRU 缓存。

只有当你真正去"看"某个层级时，它才会"坍缩"成具体的实体。在那之前，它只是一组统计数字。

这就像现实世界的量子力学——观测导致坍缩。我们的模拟世界也一样。
