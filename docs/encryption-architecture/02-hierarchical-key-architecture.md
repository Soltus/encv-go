# 分层密钥架构升级方案（信封加密 / Envelope Encryption）

> 方案日期：2026-07-08
> 目标版本：ECv5（或 ECv4.1 向后兼容扩展）
> 状态：待确认

## 一、核心思想

**将「保护数据的密钥」和「保护密钥的密钥」分开处理。**

- **数据加密密钥 (DEK, Data Encryption Key)**：随机生成，用于加密实际数据（AES-CTR）
- **密钥加密密钥 (KEK, Key Encryption Key)**：从用户密码派生，用于加密 DEK（AES-GCM 或 AES-KW）

这样换主密码时，只需要重新加密 DEK，不需要动数据本身。

```
┌─────────────────────────────────────────────────────────────────────┐
│                        密钥管理层（KEK Layer）                        │
│  ┌──────────┐    AES-GCM / AES-KW    ┌──────────────────────────┐  │
│  │ 用户密码  │ ─────────────────────▶ │ Wrapped DEK (包络后的DEK) │  │
│  │  (KEK)   │ ◀───────────────────── │  存储在文件头/Manifest    │  │
│  └──────────┘                        └────────────┬─────────────┘  │
└───────────────────────────────────────────────────┼──────────────────┘
                                                    │
                                                    ▼ 解密得到原始 DEK
┌───────────────────────────────────────────────────┼──────────────────┐
│                        数据加密层（DEK Layer）                        │
│                                                   │                  │
│              ┌─────────┐    AES-CTR    ┌──────────▼──────────┐      │
│              │ 原始 DEK │ ────────────▶ │   业务数据密文       │      │
│              │ (随机生成)│ ◀──────────── │  (视频/文档/图片等)  │      │
│              └─────────┘                └─────────────────────┘      │
└─────────────────────────────────────────────────────────────────────┘
```

## 二、为什么需要分层

### 2.1 换主密码零成本

| 场景 | 当前架构（单层） | 分层架构 |
|------|-----------------|----------|
| 换密码操作 | 解密所有数据 → 重加密所有数据 | 解密 DEK → 用新 KEK 重加密 DEK |
| 耗时 | O(文件大小) — GB 级文件数分钟 | O(1) — 几十毫秒 |
| 数据风险 | 中断可能导致数据不一致 | 原子操作，无风险 |

### 2.2 支持多密码/多用户

一个容器可以有多个 Wrapped DEK，每个用不同的 KEK 加密：
- 用户 A 的密码 → 解密 DEK → 访问数据
- 用户 B 的密码 → 解密同一个 DEK → 访问同一份数据
- 共享文件只需加密一次，多人可解密

### 2.3 密钥轮换可行

定期轮换 DEK（安全最佳实践）：
- 生成新 DEK_new
- 用旧 DEK_old 解密数据 → 用 DEK_new 重加密
- 用所有 KEK 重新包络 DEK_new
- （虽然还是要重加密数据，但这是**密钥轮换**，不是**换密码**）

## 三、算法选型

### 3.1 数据层：AES-CTR（保持不变）

| 项目 | 选择 | 理由 |
|------|------|------|
| **算法** | AES-128-CTR（默认） / AES-256-CTR（可选） | 流式性能好，支持随机访问 |
| **IV/Nonce** | 每个 Segment 独立随机 16 字节 | 与当前架构一致 |
| **完整性** | HMAC-SHA1-80（Encrypt-then-MAC） | 与当前架构一致 |

**保持不变的原因**：
- 当前数据层设计已经很成熟
- CTR 模式的流式特性是核心需求
- HMAC 完整性保护已经完善
- 改动会破坏向后兼容

### 3.2 密钥管理层：AES-GCM vs AES-KW

两种方案对比：

| 维度 | AES-256-GCM | AES-KW (RFC 3394) |
|------|-------------|-------------------|
| **标准** | NIST SP 800-38D | NIST SP 800-38F / RFC 3394 |
| **用途** | 通用认证加密 | 专用密钥包裹（Key Wrap） |
| **认证标签** | 16 字节 GCM Tag | 8 字节完整性校验（ICV） |
| **IV/Nonce** | 12 字节随机 Nonce | 固定算法，无需 Nonce |
| **输入长度** | 任意长度（DEK 16/32 字节） | 必须是 8 字节倍数（DEK 符合） |
| **Go 标准库** | crypto/aes + crypto/cipher.NewGCM | golang.org/x/crypto/nacl/secretbox（不是标准库） / 自行实现 |
| **Go 生态** | ✅ 标准库原生支持 | ⚠️ 需要第三方或自行实现 |
| **扩展能力** | 可附带 AAD（关联数据） | 仅加密密钥 |
| **误用风险** | Nonce 不能重用 | 无 Nonce，误用风险低 |

**推荐方案：AES-256-GCM**

理由：
1. Go 标准库原生支持，无需额外依赖
2. 可附带 AAD（如容器 ID、版本号等），增强绑定
3. 开发团队更熟悉 GCM 模式
4. 16 字节认证标签，安全性更高
5. 未来可扩展为 AAD 绑定更多元数据

**注意事项**：
- DEK 是随机生成的，每次换密码都用新的 GCM Nonce
- 同一个 DEK 用不同 KEK 包裹时，每个都用独立的随机 Nonce
- Nonce 重复风险极低（12 字节随机，且每次换密码都重新生成）

## 四、具体设计

### 4.1 新增字段

**在 Manifest 中新增 `wrapped_dek` 字段**（JSON 对象）：

```json
{
  "version": 4,
  "kind": "video",
  "kvi": { ... },
  "wrapped_dek": {
    "algorithm": "aes-256-gcm",
    "nonce_base64": "12字节随机Nonce的base64",
    "ciphertext_base64": "加密后的DEK的base64",
    "tag_base64": "16字节GCM标签的base64",
    "aad_base64": "可选，关联数据的base64"
  },
  "segments": [ ... ],
  ...
}
```

**字段说明**：

| 字段 | 长度 | 说明 |
|------|------|------|
| algorithm | 字符串 | 标识包裹算法，当前固定为 `aes-256-gcm` |
| nonce_base64 | 12 字节 | GCM Nonce，随机生成，base64 编码 |
| ciphertext_base64 | 16/32 字节 | 加密后的 DEK（与明文等长），base64 编码 |
| tag_base64 | 16 字节 | GCM 认证标签，base64 编码 |
| aad_base64 | 可变 | 可选关联数据（如容器 ID），base64 编码 |

### 4.2 存储位置选择

**为什么存在 Manifest 里，而不是 Header 里？**

| 位置 | 优点 | 缺点 |
|------|------|------|
| **Envelope Header** | 固定位置，读取快 | Header 空间紧张（2048 字节已基本用完），修改会破坏 CRC 计算范围 |
| **Manifest（推荐）** | 灵活扩展，不影响 Header 格式 | 需要先读 Manifest 才能拿到 DEK |

**Manifest 存储的优势**：
1. v4 Header 已经 2048 字节，SpecialID 占了 1992 字节，没有空间了
2. 不修改 Header 格式 → 完全向后兼容旧 v4 容器
3. Manifest 本身就是 JSON，加字段很容易
4. 读取流程：读 Header → 找 Manifest → 解 Manifest → 取 WrappedDEK → 解密 DEK → 解密数据

### 4.3 KEK 派生

从用户密码派生 KEK（密钥加密密钥）：

| 项目 | 说明 |
|------|------|
| **算法** | PBKDF2-SHA256（与当前一致） |
| **迭代次数** | 100,000 次（与当前一致，可考虑提升到 200,000+） |
| **盐值** | 复用现有 encrypt_salt（存储在 KVI 中） |
| **密钥长度** | 32 字节（AES-256-GCM） |

**注意**：KEK 只用于解密 DEK，不直接加密数据。

### 4.4 DEK 生成与存储

| 项目 | 说明 |
|------|------|
| **生成方式** | `crypto/rand` 安全随机生成 |
| **长度** | 16 字节（AES-128-CTR，默认）或 32 字节（AES-256-CTR，可选） |
| **生命周期** | 与容器同生命周期，直到密钥轮换 |
| **内存处理** | 解密后放在内存中，用完立即清零（可选优化） |

### 4.5 向后兼容策略

**读取旧容器（无 WrappedDEK）**：
1. 检查 Manifest 中是否有 `wrapped_dek` 字段
2. 如果没有 → 走旧流程：密码 → PBKDF2 → 直接得到 Data Key
3. 如果有 → 走新流程：密码 → PBKDF2 → KEK → GCM 解密 → DEK → 解密数据

**创建新容器**：
- 默认使用分层架构
- 可配置是否兼容旧版本（不推荐，安全性降低）

## 五、换密码流程

### 5.1 当前架构（单层）的换密码

```
1. 用旧密码解密所有数据（可能几个 GB）
2. 用新密码派生新密钥
3. 用新密钥重新加密所有数据
   └── 中途断电 → 数据损坏风险
```

### 5.2 分层架构的换密码

```
1. 验证旧密码正确（解密 WrappedDEK 得到 DEK）
2. 用新密码派生 KEK_new
3. 生成新的随机 Nonce
4. 用 KEK_new + Nonce 加密 DEK，得到 WrappedDEK_new
5. 原子替换 Manifest 中的 wrapped_dek 字段
   └── O(1) 操作，几十毫秒完成
   └── 数据文件完全不动
```

**伪代码**：

```go
func ChangePassword(container *Container, oldPassword, newPassword string) error {
    // 1. 用旧密码解密 DEK
    dek, err := DecryptDEK(container.WrappedDEK, oldPassword)
    if err != nil {
        return err // 旧密码错误
    }
    defer ClearBytes(dek) // 用完清零

    // 2. 用新密码派生 KEK
    kek := DeriveKEK(newPassword, container.Salt)

    // 3. 生成新 Nonce，用新 KEK 重新包络 DEK
    newWrappedDEK, err := EncryptDEK(dek, kek)
    if err != nil {
        return err
    }

    // 4. 原子替换（实际实现需考虑磁盘原子写入）
    container.WrappedDEK = newWrappedDEK
    return container.SaveManifest()
}
```

## 六、多密码支持（未来扩展）

### 6.1 设计思路

一个容器可以有多个「密钥入口」，每个入口对应一个密码/KEK，但都解密到同一个 DEK：

```json
{
  "wrapped_deks": [
    {
      "id": "owner-primary",
      "algorithm": "aes-256-gcm",
      "nonce_base64": "...",
      "ciphertext_base64": "...",
      "tag_base64": "...",
      "hint": "主人主密码"
    },
    {
      "id": "shared-with-alice",
      "algorithm": "aes-256-gcm",
      "nonce_base64": "...",
      "ciphertext_base64": "...",
      "tag_base64": "...",
      "hint": "Alice 的共享密码"
    }
  ]
}
```

### 6.2 使用场景

- **家庭共享**：夫妻各自有密码，都能访问同一份加密相册
- **团队协作**：多个成员各自的密码都能解密项目文档
- **应急访问**：设置一个恢复密码，忘记主密码时可用

### 6.3 注意事项

- 每个 WrappedDEK 都用独立的随机 Nonce
- 撤销访问只需删除对应的 WrappedDEK 条目
- 但撤销后必须轮换 DEK 并重新加密数据（否则被撤销的人如果之前保存了 DEK 还能访问）

## 七、安全性分析

### 7.1 安全性对比

| 攻击向量 | 当前架构 | 分层架构 |
|----------|---------|----------|
| 暴力破解密码 | PBKDF2 100k 迭代保护 | PBKDF2 100k 迭代保护（相同） |
| DEK 泄露 | N/A（无 DEK） | DEK 在内存中，用完应清零 |
| Nonce 重用 | 每个 Segment 独立 Nonce | 每个 Segment + 每个 WrappedDEK 都独立 |
| 密码修改风险 | 重加密过程中断 → 数据损坏 | 原子操作，无风险 |

### 7.2 潜在风险与缓解

| 风险 | 缓解措施 |
|------|---------|
| DEK 在内存中被窃取 | 敏感操作完成后立即清零 DEK；使用 memguard 等库 |
| GCM Nonce 重用 | 每次加密 DEK 都用全新随机 12 字节 Nonce |
| KDF 迭代次数不足 | 可考虑从 100k 提升到 200k+（权衡性能与安全） |
