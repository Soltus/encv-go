# ENCV 容器架构 v2: 分层堡垒

以SCCGV视频容器为例

## 1. 设计哲学

ENCV v2.1 架构的核心目标是构建一个健壮、高性能、高扩展性且易于维护的加密容器格式。我们称之为“分层堡垒”，因为它像一座现代化的堡垒，层层设防，职责分明。

* **健壮性**：通过多层校验和冗余设计，实现数据损坏时的精确定位、隔离与恢复，确保核心服务（如播放）不中断。
* **高性能**：通过 O(1) 精确寻址和分片独立校验，实现低内存占用的流式播放和安全的并发读取。
* **扩展性**：通过结构化的元数据和插件化架构，使未来添加新功能（如新容器类型、新元数据）变得简单且不破坏兼容性。
* **简洁性**：通过清晰的分层和抽象，降低核心逻辑的复杂度，让开发和维护更轻松。

## 2. 整体文件布局

ENCV 容器由四个逻辑层构成，从外到内分别是：信封层、清单层、数据层和恢复层。

```
+--------------------------------------------------------------------------------------+
|                                ENCV 容器文件 (.sccgv)                                |
|                                                                                      |
|  +----------------------------------------------------------------------------- <-- L1: Envelope (信封层)
|  |                  L1: Envelope Header (16 bytes)                               |
|  |  - Magic "ENCV" (4)  - Version (2)  - Flags (2)  - Reserved (8)            |
|  +-----------------------------------------------------------------------------+
|  |                                                                             |
|  |  +----------------------------------------------------------------------- <-- L2: Manifest (清单层)
|  |  |                       L2: Manifest Block                             |
|  |  |  - Block Header (Type, Len, CRC32)                                    |
|  |  |  - Manifest Data (JSON)                                              |
|  |  |    { "version": "...",                                               |
|  |  |      "kvi": { "salt_base64": "...", "iv_base64": "..." },           |
|  |  |      "fragments": [                                                  |
|  |  |        { "id": "kvi", "type": "metadata", "len": 1024 },           |
|  |  |        { "id": "main_data", "type": "data", "offset": 0,            |
|  |  |          "len": 1234567890 }                                        |
|  |  |      ],                                                             |
|  |  |      "redundancy": { "kvi_backup_crc": "..." } }                    |
|  |  +-----------------------------------------------------------------------+
|  |                                                                             |
|  |  +----------------------------------------------------------------------- <-- L3: Data Streams (数据层)
|  |  |                      L3: Fragment "kvi" (KVI)                        |
|  |  |  - Block Header (Type, Len, CRC32)                                    |
|  |  |  - KVI Data (JSON)                                                    |
|  |  +-----------------------------------------------------------------------+
|  |  |                   L3: Fragment "main_data" (Data)                   |
|  |  |  - Block Header (Type, Len, CRC32)                                    |
|  |  |  - Encrypted Data Stream                                               |
|  |  +-----------------------------------------------------------------------+
|  |  |                      ... (更多数据分片)                                |
|  |  +-----------------------------------------------------------------------+
|  |                                                                             |
|  |  +----------------------------------------------------------------------- <-- L4: Recovery (恢复层, 可选)
|  |  |                    L4: Recovery Block                                |
|  |  |  - Block Header (Type, Len, CRC32)                                    |
|  |  |  - Reed-Solomon Parity Data / KVI Backup                             |
|  |  +-----------------------------------------------------------------------+
|  |                                                                             |
|  +-----------------------------------------------------------------------------+
|                                                                                      |
|  +----------------------------------------------------------------------------- <-- L1: Envelope (信封层)
|  |                   L1: Envelope Footer (32 bytes)                            |
|  |  - Magic "ENCV" (4)  - Manifest Offset (8)  - Manifest Len (8)             |
|  |  - Manifest CRC32 (4)  - Global CRC32 (4)  - Reserved (4)                 |
|  +-----------------------------------------------------------------------------+
|                                                                                      |
+--------------------------------------------------------------------------------------+
```

## 3. 分层详解

### L1: Envelope (信封层)

* **职责**: 快速识别、精确定位、全局校验。
* **结构**: 固定大小的 Header 和 Footer。
* **工作流程**: 程序首先读取文件末尾的 Footer，通过 Magic Number 确认文件类型，并获取 L2 清单层的精确位置 (`Manifest Offset`) 和完整性 (`Manifest CRC32`)。
* **容错**: Header 和 Footer 的双重 Magic Number 设计，即使在文件不完整（如下载未完成）的情况下也能进行识别。

### L2: Manifest (清单层)

* **职责**: 元数据中心、版本控制、冗余备份。
* **结构**: 一个独立的 Block，内部使用 JSON 格式存储元数据。
* **核心内容**:
  * `kvi`: 加密所需的 Salt 和 IV。
  * `fragments`: 所有数据块的索引表，是高性能寻址和通用性的关键。
  * `redundancy`: 存储关键数据（如 KVI）的备份 CRC，用于 L3 数据损坏时的恢复。
* **容错**: L2 本身被 L1 的 CRC32 保护。其内部的 `redundancy` 字段为 L3 的数据提供了第二道防线。

### L3: Data Streams (数据层)

* **职责**: 纯粹的数据存储、独立校验、并发基础。
* **结构**: 一系列独立的 Block，每个 Block 包含一个数据分片（包括 KVI 本身）。
* **工作流程**: 每个块都有自己的 `Block Header`，包含类型、长度和 CRC32。读取时立即校验，实现错误的快速隔离。
* **容错**: 一个块的损坏完全不影响其他块。AES-CTR 模式确保了即使块 N 损坏，块 N+1 仍可完美解密。

### L4: Recovery (恢复层)

* **职责**: 高级数据恢复。
* **结构**: 可选的 Block。
* **工作流程**: 可用于存储 Reed-Solomon 纠删码，在少量数据块损坏时进行数据重建。
* **容错**: 这是最高级别的容错机制，可在数据层之上提供更强的恢复能力。在项目初期可完全忽略，不影响核心功能。

## 5. 通用性：单文件与分片容器的统一

新架构通过 L2 清单层，将单文件和分片容器视为同一数据模型的不同表现，处理逻辑完全统一。

#### 场景 A: 单文件容器

```
L2 Manifest JSON:
{
  "fragments": [
    { "id": "kvi", "type": "metadata", "len": 1024 },
    { "id": "main_data", "type": "data", "offset": 0, "len": 1234567890 } // 只有1个数据分片
  ]
}
```

#### 场景 B: 分片容器

```
L2 Manifest JSON:
{
  "fragments": [
    { "id": "kvi", "type": "metadata", "len": 1024 },
    { "id": "part_000", "type": "data", "filename": "movie.000.sccgi", "len": 10485760 }, // 指向外部
    { "id": "part_001", "type": "data", "filename": "movie.001.sccgi", "len": 10485760 }
  ]
}
```

**统一处理逻辑**: 上层的 `SeekableDecryptReader` 只关心 L2 提供的 `fragments` 列表。它会遍历这个列表，并根据每个 fragment 的 `type` 和 `filename` 字段来决定是从内部读取还是打开外部文件。核心的解密和流式拼接逻辑完全相同。

## 6. 架构优势总结

| 特性                 | 旧架构                               | 新架构                                                           |
| :------------------- | :----------------------------------- | :--------------------------------------------------------------- |
| **分片定位**   | 依赖不准确的头部计算或线性扫描       | **L1 Footer 提供 O(1) 精确映射**                           |
| **内存管理**   | 每个分片可能分配大缓冲区，缺乏复用   | **固定大小的缓冲区池，全局复用**                           |
| **错误恢复**   | 一个分片损坏可能导致整个容器无法读取 | **L1/L2/L3 三重 CRC 校验，错误被精准隔离和恢复**           |
| **预读/并发**  | 难以实现，边界不清晰，易错乱         | **L2 精确映射，L3 独立校验，可安全预读和并行处理**         |
| **扩展性**     | 需要为每种容器注册复杂的处理器链     | **L2 清单和插件模式，添加新功能只需扩展 JSON 和注册插件**  |
| **开发复杂度** | 逻辑分散，难以维护和调试             | **分层架构职责清晰，每层接口简单，开发和维护成本大大降低** |

## 结论

ENCV v2.1 “分层堡垒”架构通过其精巧的分层设计，不仅彻底解决了旧架构的所有痛点，更为 `encv` 项目构建了一个坚不可摧、面向未来的技术核心。它实现了性能、容错、扩展性和开发复杂度的完美平衡，是项目长期发展的坚实基石。

**推理结束**

当然可以！这正是我们设计的“分层堡垒”架构最强大的特性之一。 **一个块损坏，视频依然可以寻址、播放和解密** ，只是会跳过损坏的部分。

这得益于两个核心技术：

1. **AES-CTR 流密码的特性** ：CTR 模式是一种流密码。每个数据块的解密都是独立的，不依赖于前一个块。这意味着即使块 `N` 的数据完全损坏，块 `N+1` 依然可以被完美解密，不会产生“错误扩散”。
2. **分层架构的精确寻址** ：L2 清单层提供了完整的“地图”，L3 的每个块都有独立的 CRC32 校验。这使得我们能 **精确地知道哪个块坏了，以及如何跳到下一个好块** 。


### 关键步骤详解

#### 1. 检测与隔离

当 `SeekableDecryptReader` 尝试读取一个数据块时，它首先会读取该块的 `BlockHeader`，然后对数据部分进行 CRC32 校验。

```
// 伪代码
func (r *SeekableDecryptReader) readFragment(f *Fragment) ([]byte, error) {
    // 1. 读取块头
    header, err := readBlockHeader(r.file, f.Offset)
    if err != nil {
        return nil, err
    }

    // 2. 读取块数据
    data := make([]byte, header.Length)
    _, err = io.ReadFull(r.file, data)
    if err != nil {
        return nil, err
    }

    // 3. 【关键】校验 CRC32
    if actualCRC := crc32.ChecksumIEEE(data); actualCRC != header.CRC32 {
        // 损坏！记录日志，并返回一个特殊的错误
        log.Printf("WARN: Fragment %s at offset %d is corrupted (CRC mismatch)", f.ID, f.Offset)
        return nil, ErrFragmentCorrupted
    }

    return data, nil
}
```

#### 2. 寻址下一个块

一旦检测到 `ErrFragmentCorrupted`，我们的 `Read` 方法不会向上层（播放器）返回错误，而是内部处理。

它会查询已加载的 L2 清单，找到当前损坏块的下一个块，并准备好读取它。

#### 3. 错误隐藏

这是影响用户体验的关键一步。播放器期望一个连续的数据流。如果我们直接跳过损坏块，视频的音画就会与时间轴错位。因此，我们必须“填补”这个空缺。

**策略 A (简单实现 - 零填充):**
最简单的方法是生成与损坏块等长的全零数据（对于视频）或静音数据（对于音频）。

```
// 伪代码
func (r *SeekableDecryptReader) Read(p []byte) (n int, err error) {
    // ... 循环读取数据直到填满 p ...

    // 尝试读取当前块
    data, err := r.readFragment(r.currentFragment)
    if err == ErrFragmentCorrupted {
        // 生成占位数据
        placeholder := make([]byte, r.currentFragment.Length)
        // 解密占位数据 (解密全零数据仍然是全零)
        decryptedPlaceholder, _ := r.decrypter.Decrypt(placeholder)
  
        // 将占位数据复制到输出缓冲区
        n = copy(p, decryptedPlaceholder)
        // 更新状态，准备读取下一个块
        r.moveToNextFragment()
        return n, nil // 注意：这里返回 nil error，让播放器以为一切正常
    }
  
    // ... 正常解密和复制逻辑 ...
}
```

**策略 B (高级实现 - 帧重复/插值):**
对于更好的用户体验，可以：

* **视频** ：重复损坏块之前的最后一帧。
* **音频** ：重复损坏块之前的最后一个音频样本。

这需要对解密后的数据格式有更深入的理解，实现起来更复杂，但效果更平滑。

### 总结：新架构的容错能力

| 特性                 | 旧架构                         | 新架构                                                 |
| -------------------- | ------------------------------ | ------------------------------------------------------ |
| **块损坏检测** | 困难，可能导致整个文件解析失败 | **轻松** ，每个块独立 CRC32 校验                 |
| **损坏定位**   | 模糊，难以精确定位问题区域     | **精确** ，L2 清单提供完整地图                   |
| **损坏后恢复** | 几乎不可能，程序崩溃或卡死     | **无缝** ，自动跳过损坏块，继续播放              |
| **用户体验**   | 糟糕，播放中断                 | **良好** ，可能会有短暂的卡顿/花屏，但播放不中断 |

## 非常有必要将“原子文件”与“可寻址流”分开处理。

| 特性                   | 统一处理 (全部用 Seekable) | 分离处理 (Simple vs Seekable)         | 评估               |
| ---------------------- | -------------------------- | ------------------------------------- | ------------------ |
| **语义清晰度**   | 低，意图模糊，需要猜测     | **高** ，类型即意图，一目了然   | **分离胜出** |
| **实现复杂度**   | 高，一个“上帝类” Reader  | **低** ，两个职责单一的 Reader  | **分离胜出** |
| **维护成本**     | 高，修改一处可能影响另一处 | **低** ，逻辑隔离，互不影响     | **分离胜出** |
| **原子文件性能** | 低，承担不必要的 Seek 开销 | **高** ，轻量级，无额外开销     | **分离胜出** |
| **容错策略**     | 混乱，逻辑复杂，易出错     | **清晰** ，不同类型采用不同策略 | **分离胜出** |
| **未来扩展性**   | 差，新功能污染现有逻辑     | **好** ，可为不同类型独立扩展   | **分离胜出** |
