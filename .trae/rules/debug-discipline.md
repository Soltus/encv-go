# 调试纪律铁律（严禁甩锅用户、严禁无效猜测）

> **核心原则：用户报告 bug = 真实存在 bug。你的测试通过 ≠ 代码正确。**
> **找不到 bug 时，禁止说"我这边没问题"、"测试通过了"、"应该没问题"。**
> **必须用真实端到端测试（Cypress / HTTP 集成测试）复现错误，而不是写一个不覆盖真实场景的单元测试然后宣称通过。**

> 创建：2026-07-02（用户严厉批评一小时无效猜测 + 甩锅用户 + 反复肯定自己没错）

---

## 一、严禁行为（违反 = 严重错误）

### 1.1 严禁甩锅用户

**用户报告 bug 时，禁止以下行为**：

| 禁止行为 | 原因 |
|---------|------|
| "我这边测试通过了" | 你的测试没覆盖真实场景，通过毫无意义 |
| "应该是前端的问题" | 没验证就甩锅，浪费时间 |
| "可能是网络/缓存问题" | 没有证据的猜测 |
| "试试重启/清除缓存" | 不解决根因，只掩盖症状 |
| "这个逻辑看起来是对的" | "看起来"对不等于实际对 |

**正确行为**：用户说搜不到 → 必须找到搜不到的根因 → 修复 → 验证修复后能搜到。

### 1.2 严禁无效猜测

**禁止"猜测→否定→再猜测"循环**。每次猜测必须有证据支撑。

**错误模式（浪费时间）**：
```
猜测1：可能是 maxResults 截断 → 没验证 → 放弃
猜测2：可能是路径编码问题 → 没验证 → 放弃
猜测3：可能是 webdav 索引冲突 → 没验证 → 放弃
猜测4：可能是容器扩展名过滤 → 没验证 → 放弃
... 一小时后仍在猜测 ...
```

**正确模式**：
```
1. 写测试复现 bug（必须与真实场景一致）
2. 测试失败 → 找到 bug
3. 测试通过 → 测试场景不对，加更多真实因素
4. 重复直到测试失败 → 找到 bug
```

### 1.3 严禁"肯定自己没错"

**测试通过不代表代码正确**。如果用户说有问题，但你的测试通过，说明：

1. **测试场景不匹配真实环境**（最常见）
2. **测试断言不够严格**
3. **测试缺少关键前置条件**
4. **测试数量严重不足**（见 §1.6）

**禁止在测试通过后说"代码没问题"**。必须分析测试与真实环境的差异，补全测试直到能复现 bug。

### 1.6 严禁"两个用例就敢声称覆盖"（测试规模铁律）

**复杂逻辑的边界情况数量级远超直觉**。"我写了测试且通过"不等于"逻辑被覆盖"。

**铁律：测试数量必须与被测逻辑的边界空间匹配，不允许用 2-3 个用例糊弄复杂逻辑。**

| 逻辑类型 | 最少用例数 | 说明 |
|---------|----------|------|
| 简单纯函数（1-2 个分支） | 3-5 | 正常 + 边界 + 异常 |
| 分词 / token 化 | **30+** | 中文/英文/混合/标点/空格/大小写/单字/多字/特殊符号/unicode |
| 向量搜索 + 过滤 | **50+** | 短查询/长查询/空查询/单字/多 token/无匹配/全匹配/边界 score |
| 搜索结果合并（关键词 + 向量 + fallback） | **80+** | 三路组合 × 各路边界 × 排序/去重/贪婪/严格 |
| 完整搜索端点（HTTP 端到端） | **100+** | 上述组合 × 路径前缀 × 挂载点 × 索引状态 × 递归参数 |

**禁止行为**：
| 禁止 | 原因 |
|------|------|
| "搜了 1 个词命中 1 个文件，测试通过" | 没覆盖空查询、无匹配、多匹配、干扰项、贪婪/严格切换 |
| "向量搜索有结果就算通过" | 没验证不相关结果被过滤、score 排序、阈值边界 |
| "前端搜索框输入有响应就算通过" | 没测大量数据、防抖、并发请求、清空、特殊字符 |

**正确做法**：
1. 列出所有边界维度（语言/长度/字符类别/空格/大小写/标点/unicode/空/单字/多 token）
2. 笛卡尔积生成测试矩阵（即使简化也要覆盖每个维度的至少一个代表值）
3. 干扰项必须有（只共享部分 token 的文件）—— 没有干扰项的搜索测试毫无价值
4. 每个修复的 bug 必须有"修复前 FAIL / 修复后 PASS"的对应测试
5. 边界用例（空字符串、单字、超长、纯标点、纯 emoji）必须显式覆盖

**反例（本项目 2026-07-02 踩坑）**：
- 搜索"在线视频"返回不相关结果（"在线文档.pdf"），用户的真实环境有大量共享单个 bigram 的弱相关文件
- 测试只放了 2 个文件名（"在线播放-高清视频.mp4" + "在线文档.pdf"），声称"测试通过"
- 实际上没覆盖：纯英文查询、混合查询、单字查询、空查询、超长查询、emoji 文件名、共享 0/1/2/3 个 bigram 的各种干扰项
- **用户实测依然有问题** —— 测试根本没暴露真实场景

**强制要求**：搜索/分词类逻辑 PR 必须附带测试用例数量统计（`go test -v -run TestX | grep -c '^=== RUN'`），低于 30 个用例的搜索测试不予合并。

### 1.4 严禁偷懒思维

**禁止在思考过程中出现以下内容**：

| 禁止内容 | 原因 |
|---------|------|
| "时间有限" | 没有时间限制，认真做完 |
| "这太复杂了" | 复杂不是偷懒的理由 |
| "先这样吧" | 没解决的问题不会自己消失 |
| "差不多就行了" | 差不多 = 没解决 |
| "暂时跳过" | 跳过 = 遗忘 = 再犯 |
| "依赖没装，换个简单方法" | 简单方法不等于正确方法。Xvfb 没装就去装，不是换 curl 替代 Cypress |
| "环境不支持，用 mock 吧" | 真实 bug 必须在真实环境复现，mock 只会掩盖问题 |
| "这个测试跑不起来，跳过吧" | 测试跑不起来是环境问题，先修环境 |
| "用单元测试替代 E2E 吧" | 单元测试覆盖不了端到端链路，不能替代 |

**偷懒思维的共同特征**：用"更简单"的方式替代正确的方式，结果没真正解决问题。

### 1.5 严禁擅自修改递归规则来"绕过"bug

**禁止在未询问用户的情况下修改 `/d` 的递归搜索行为来"修复"顶层搜索问题。**

`/d` 的搜索必须严格遵守 `recursive` 参数：
- `recursive=true` → 递归搜索所有挂载点下的所有文件
- `recursive=false` → 只搜索各挂载点根目录

**任何修改让 `/d` 不遵守递归规则的行为都是严重错误**，包括但不限于：
- 把递归搜索改成非递归"因为递归太慢"
- 把非递归搜索改成递归"因为用户想搜全部"
- 在 `/d` 路径上硬编码 `recursive=true`
- 在 `/d` 路径上忽略 `recursive` 参数

**如果认为递归规则有问题，必须先询问用户，说明理由，得到确认后才能修改。**

**修复 bug 的正确思维**：找到真正的根因（如端点没有共用搜索逻辑），修复根因，而不是修改正确的行为规则来"绕过"问题。

## 二、正确调试流程（强制）

### 2.1 复现优先

**第一步永远是复现 bug**，不是读代码猜原因。

| Bug 类型 | 复现方式 |
|---------|---------|
| 前端可见的 bug（搜索不到、显示错误等） | **Cypress E2E 测试**（必须走真实 HTTP API） |
| 后端 API bug | **Go 集成测试**（启动真实 server + HTTP 请求） |
| 编译/构建 bug | **CI 复现**（用相同构建参数） |

### 2.2 Cypress 测试铁律

**前端可见 bug 必须用 Cypress 复现**，不是写 Go 单元测试然后宣称通过。

**Cypress 测试必须**：
1. 启动真实后端（不是 mock）
2. 调用真实 API 端点
3. 验证用户可见的结果（搜索结果列表）
4. 覆盖用户报告的精确场景（路径、关键词、参数）

**禁止**：
- 用 Go 单元测试替代 Cypress 测试来"验证"前端可见 bug
- 用 mock 数据替代真实后端
- 测试通过后说"代码没问题"

### 2.3 差异分析

**如果测试通过但用户说有问题，必须分析差异**：

| 差异维度 | 检查项 |
|---------|--------|
| 数据量 | 测试 2 个文件 vs 真实环境几千个文件 |
| 目录深度 | 测试 1-2 层 vs 真实环境 N 层嵌套 |
| 文件名 | 测试简单 ASCII vs 真实环境中文/特殊字符 |
| 挂载点配置 | 测试默认配置 vs 真实环境自定义挂载 |
| 索引状态 | 测试索引已构建 vs 真实环境索引可能未构建/过期 |
| WebDAV 状态 | 测试无容器文件 vs 真实环境有容器文件 |
| 并发 | 测试单线程 vs 真实环境多请求并发 |

### 2.4 修复验证

**修复后必须验证**：
1. 原来失败的测试现在通过
2. 没有破坏其他功能（运行相关测试）
3. 分析修复是否引入新问题

## 三、搜索功能专项规则

### 3.1 挂载点搜索独立于 WebDAV

**挂载点（mount registry）是物理文件系统的抽象，与 WebDAV 无关。**

- 物理文件搜索：遍历 `mountRegistry.List()`，对每个挂载点调用 `SearchFiles`
- WebDAV 虚拟文件搜索：遍历 `webdavFSByMount`，搜索容器文件展开后的虚拟文件
- 两者是独立的来源，结果合并返回

**禁止让挂载点搜索依赖 WebDAV 启用配置。** 即使 WebDAV 没启用，物理文件搜索也应该正常工作。

### 3.2 顶层 /d 搜索铁律

**`/d` 搜索必须遍历所有启用的挂载点**，不能只搜默认挂载点。

```go
// ✅ 正确：遍历所有挂载点
for _, m := range s.mountRegistry.List() {
    if !m.Enabled { continue }
    results, _ := s.mobileSvc.SearchFiles("/d/"+m.Name, keyword, recursive)
    // ...
}

// ❌ 错误：只搜默认挂载点
results, _ := s.mobileSvc.SearchFiles("/", keyword, recursive)
```

### 3.3 索引搜索路径转换

**索引中的路径是相对于 servingDir 的物理路径，不是虚拟路径。**

- 索引路径：`/下载/思源笔记.zip`（相对于 servingDir）
- 虚拟路径：`/d/primary/下载/思源笔记.zip`（前端路径）

**搜索时必须正确转换**：
1. 将虚拟查询路径转为索引路径前缀
2. 用索引路径前缀过滤索引条目
3. 将匹配的索引路径转回虚拟路径返回给前端

### 3.4 搜索结果不能被截断

**`maxResults` 限制不应导致用户搜不到文件。**

如果文件名匹配关键词，它必须在结果中，不管目录遍历顺序如何。

**当前问题**：`SearchFiles` 中 `maxResults = 200`，如果前 200 个结果都是别的文件，目标文件就被截断了。

**修复方向**：
- 索引搜索：遍历全部索引条目，先收集所有匹配结果，再按相关性排序截断
- WalkDir 搜索：同上

### 3.5 智能搜索策略：分词 + 向量综合（结果过少贪婪，结果过多严格）

**核心原则：单一搜索路径无法覆盖所有场景，必须根据结果数量动态切换策略。**

| 结果数量 | 策略 | 目的 |
|---------|------|------|
| 关键词精确匹配 ≥ 阈值（如 20） | **严格模式**：只返回关键词匹配结果 | 避免向量噪声淹没精确匹配 |
| 关键词匹配 1~19 | **综合模式**：关键词结果 + 向量重排序 | 精确匹配为主，向量补充相关项 |
| 关键词匹配 0 | **贪婪模式**：纯向量搜索 fallback | 不让用户看到空结果 |

**贪婪模式必须前端可见**：
- 后端响应携带 `search_mode: "greedy" | "strict" | "combined"` 字段
- 前端对 `greedy` 模式的结果加视觉标记（虚线边框 / 不同底色 / "贪婪匹配"徽章）
- 用户必须能一眼看出"这些结果是宽松匹配，可能不完全相关"

**贪婪模式的过滤强度**：
- 结果过少时（< 5）：放宽 bigram 重叠要求（共享 ≥ 1 个 bigram 即可）
- 结果中等（5~20）：当前规则（共享 ≥ 一半 bigram）
- 结果过多（> 20）：收紧要求（共享全部 bigram 或 score ≥ 0.5）

**禁止行为**：
| 禁止 | 原因 |
|------|------|
| 静默 fallback 到向量搜索不告知用户 | 用户以为精确匹配，实际是宽松匹配 |
| 贪婪模式返回空就当无结果 | 贪婪的本意就是"宁多勿少" |
| 严格模式永远不触发 | 大量精确匹配时向量噪声会淹没结果 |

### 3.6 libSQL 原生向量支持（不得误判为不支持）

**libSQL 原生支持 `vector_distance_cos` 等 SQL 向量函数，无需任何扩展。**

参考：https://docs.turso.tech/features/ai-and-embeddings
> "Vector Similarity Search is built into Turso and libSQL Server as a native feature."
> "Turso and libSQL enable vector search capability without an extension."

**铁律**：
1. **SHALL** libsql 驱动走 `TursoStore`（用原生 `vector_distance_cos` SQL 函数）
2. **SHALL NOT** 把 libsql 降级到 `SQLiteStore`（Go 层计算）—— 除非有实测证据证明该 .so 编译时禁用了向量支持
3. **SHALL** 验证 libsql 向量支持时写真实 SQL 测试（`SELECT vector_distance_cos(...)`），不是看 driver 代码猜
4. **SHALL** 若实测发现 libsql 不支持向量（极少数自定义编译），按 [graceful-degradation.md](./graceful-degradation.md) L2 级降级：日志 WARN + `/api/runtime` 暴露 + 走 SQLiteStore 兜底

**历史踩坑（2026-07-02）**：
- 错误假设："本地嵌入式 libsql（CGO .so）不支持 vector_distance_cos"
- 实际：libSQL 原生支持向量，文档明确写"without an extension"
- 错误修复：把 libsql 从 TursoStore 改到 SQLiteStore，性能下降且未利用原生索引
- 正确做法：写 SQL 测试验证，若支持就走 TursoStore

### 3.7 搜索测试必须包含干扰项

**没有干扰项的搜索测试 = 毫无价值。**

干扰项设计要求：
- **弱相关干扰项**：只共享 1 个常见 bigram（如查询"在线视频"，干扰项"在线文档.pdf"只共享"在线"）
- **零相关干扰项**：完全无 bigram 重叠（如"无关文件.txt"）
- **强相关干扰项**：共享全部 bigram 但语义不同（如查询"在线视频"，干扰项"在线视频下载工具.exe"）
- **跨语言干扰项**：英文查询 + 中文文件名 / 反之

每个搜索测试至少包含 3 类干扰项各 1 个，否则不予合并。

## 四、违反本规则的后果

| 违反行为 | 后果 |
|---------|------|
| 甩锅用户 | 立即停止，重新开始调试 |
| 无效猜测循环 | 必须切换到测试复现模式 |
| 测试通过后说"没问题" | 必须分析测试与真实环境的差异 |
| 偷懒思维 | 立即纠正，认真完成 |
| 修改递归规则绕过 bug | 回滚修改，找到真正的根因 |
